## できた条件

- 節のブラインド査読と汎用のブラインド委譲が、既存の直接 API 実装から抽出した一つの Rust 関数を使う。両入口の模擬試験が通り、従来のリクエスト本文と確認範囲の扱いを保つ。新しい呼び出し元は指示と資料だけで本文と使用量を得られる。
- Anthropic Messages と OpenAI Responses を別々に試し、送信本文のツール集合が空で、履歴・ファイル参照・無関係な検出用文字列を含まないことを確かめる。ツールを要求する応答、認証不足、拒否、途中打ち切り、指定モデルの不一致を失敗として示し、通常エージェントや別の課金経路が呼ばれないことを確かめる。
- 送信前に指示・資料の全文と順序、組み立てた入力、経路・版・設定をワークスペースごとのリポジトリ外の非公開サーバー状態に固定する。元の資料と規則を変更してから再実行しても、同じ経路へ同じリクエスト本文が渡る。保存の失敗時は送信せず、記録に認証の秘密を残さない。API の従量経路と、返された使用量または不明な項目が分かる。
