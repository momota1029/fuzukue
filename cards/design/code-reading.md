コード読解と小規模な編集を、研究資料と同じワークスペースで行えるようにする。

## 今あるもの

- ソース画面は `gpui-kit` の `Editor` を使う。拡張子、Makefile などのファイル名、先頭行の shebang から言語を選ぶ。未判定のファイルも UTF-8 のテキストとして開ける。
- tree-sitter で色付けし、アウトラインとガターの折りたたみに構文木を使う。同梱文法は Rust、Python、C、C++、Go、Java、JavaScript、TypeScript、TSX、JSON、TOML、YAML、Markdown、Bash、Make、CMake、SQL、HTML、CSS、Lua、Zig、Kotlin、Swift、Scala、Ruby。R、Julia、Lean、LaTeX は crates.io の生成済み C パーサーを追加した。追加した版は `tree-sitter-r` 1.3.0、`tree-sitter-julia` 0.23.1、`arborium-lean` 2.18.2、`codebook-tree-sitter-latex` 0.6.1。いずれも選定時点で公開から 2 週間以上経過している。
- エディタ（vendor の `gpui-base` の `input/editor`）には、色付けの差し込み口（`InputHighlighter`）と、LSP の各機能の差し込み口（補完、ホバー、定義へ飛ぶ、意味的な色付け、診断、コードアクション）がある。

## 方針

1. **色付けと構造は tree-sitter**: `gpui-kit` の `tree-sitter` 機能に切り替え、同梱の文法を使う。R、Julia、Lean、LaTeX は crates.io の文法を使う。関数・型の一覧（アウトライン）と折りたたみも tree-sitter の構文木から作る。
2. **language server はサーバーで動かす**: サーバーに LSP の取り次ぎを置き、ワークスペースごと・言語ごとに language server を起動する（起動はファイルを開いたとき、しばらく使われなければ止める）。設定は `fuzukue.toml` か利用者の設定に 1 行で書く（例: `rust = "rust-analyzer"`、`python = "basedpyright-langserver --stdio"`、`r = "R --slave -e languageserver::run()"`、`julia = ...`、`lean = "lake serve"`）。既定の候補を見つけて提案するが、勝手に入れはしない。クライアントのエディタの LSP の差し込み口へ、プロトコル越しに結果を渡す。
3. **同じ索引に入れる**: language server から取った記号（定義、参照、呼び出し階層）を、研究の記号の索引と同じ形で持ち、論文の定義とコードの実装をまたいで「定義へ飛ぶ / 使っている所」が効くようにする。作業役も同じ道具で引く。自分のコードと取得した他人のコードは区別せず、違いは出典（どこから、いつ、どの版）の記録だけ。
4. **流れで読む**: 呼び出しの関係に加えて、ファイルの読み書き（`read_csv`、`open`、`savefig` などの呼び出しを tree-sitter の問い合わせで拾う）からデータの流れのグラフを作り、図や表を作ったコードへ飛べるようにする。ノートブック（`.ipynb`）は出力ごと表示する。データのファイル（CSV、TSV、parquet）は先頭の行と列ごとの要約（型、欠損、分布）を出す。
5. **テストは必須**: プロジェクトのテストの走らせ方を見つける（`Cargo.toml` → `cargo test`、`pyproject.toml`/`pytest.ini` → `pytest`、`DESCRIPTION` → `testthat`、`Project.toml` → `Pkg.test`、`lakefile` → `lake build` と axioms の確認、`Makefile` の `test`）。見つからなければ設定に書く。画面と作業役の道具（`run_tests`）から走らせ、失敗はファイルと行へ飛べる形で出す。作業役の変更は、テストが通るまで完了にしない。統計の再現（乱数の種、パッケージの版、決まった範囲の実行と論文の数字の照合）も「テスト」として登録できる。
6. **fuzukue 自身のビルド**: サーバーのビルド、テスト、指定した撮影とクライアント配布を順に走らせる。全ワークスペースが空いてからサーバーを入れ替え、クライアントは [[distribution]] の経路で更新する。設定と入れ替え時の動きは [[self-update]] にまとめた。

## 書く

- ソースの画面を読み取り専用から編集できる形にする。土台は今のカード編集と同じ `gpui-kit` の `Editor`（日本語入力、選択、取り消しはすでに動く）。
- 一つのファイル全体でも、関数や型を一つだけ（tree-sitter の構文木で範囲を決め、カードのように）開いても書ける。
- 書くときに効くもの: 色付けと折りたたみ（tree-sitter）、補完・ホバー・定義へ飛ぶ・エラー表示（language server）、ファイル内の検索と置換、保存時の整形（`rustfmt`、`ruff format`、`styler` などを設定で）、開いているファイルのタブ。
- やらないもの（Zed に任せる）: 複数カーソル、分割画面、拡張機能、端末。
- 編集を閉じたときとビルドしたときに、人の編集を指示として整合を取る（[[human-edits]]）。

### 段階 1 の実装

- カードのファイルリンクや記号の検索結果から開ける。任意のファイルは Ctrl+K で `file: src/lib.rs` のようにワークスペース相対パスを入力して開く。タブの丸印は未保存の変更を表す。Ctrl+F で検索、Ctrl+H で置換、Ctrl+S で保存する。
- アウトラインの項目を押すと行へ移動する。未保存の変更がないときに「範囲を編集」を押すと関数や型の範囲だけを開く。範囲の保存は、開いた版のファイル全体を照合してから、その範囲を差し替える。
- 保存はサーバー側でファイル全体の SHA-256 を比較し、同じディレクトリの一時ファイルから原子的に置き換える。競合時はディスク版と編集中の全体との差分を表示する。ディスク版を開く、表示中の版を確認して上書きする、編集に戻る、のいずれかを選べる。上書き時にも表示したディスク版と照合する。ワークスペース外と UTF-8 のテキスト以外は編集対象外（`~/research` も 2026-11-21 から編集できる）。
- 保存時の整形はサーバー利用者のワークスペース別状態ディレクトリにある `editor.toml` で設定する。起動ログの `state:` にそのディレクトリを表示する。既定の場所は `~/.local/state/fuzukue/<ワークスペース識別子>/editor.toml`。コマンドはサーバー側のワークスペースを作業ディレクトリとして、全体を標準入力で渡し、標準出力を保存する。ツールは事前に利用者が用意する。整形が失敗した場合は編集内容を保持する。範囲編集で整形により内容が変わったときは、保存後に整形済みのファイル全体を表示する。

  ```toml
  [format_on_save]
  rust = "rustfmt --emit stdout"
  python = "ruff format -"
  ```

- プロトコル 19 で編集タブの保存・競合結果と `editor_closed`、`build_started` を追加した。編集したタブを明示的に閉じたときと、既存の PDF ビルドが開始したときにワークスペースの履歴へ記録して配信する。
- カードのファイルを保存したソースタブを閉じると、保存前の控えをそのデッキの[[human-edits|整合確認]]に回す。

### 段階 2 の実装

- ワークスペースと配下のプロジェクトで Rust、pytest、R、Julia、Lean、Make、npm のテストを検出する。Cargo ワークスペースは `cargo test --workspace` で実行する。pytest は `pyproject.toml`、`pytest.ini`、`setup.cfg` の `[tool:pytest]`、または `tests/` 配下の `test_*.py` を探す。Lean は `lake build` の後、ファイル名に `audit` または `axiom` を含む Lean ファイルに `#print axioms` があれば、その監査を `lake env lean` で実行し、公理依存を確認する。
- `fuzukue.toml` の `[tests.<名前>]` は、その設定を置いたプロジェクトと指定先の作業ディレクトリの自動検出に優先する。`command` は引数の配列または引用符付きのコマンド文字列。`cwd` は設定ファイルのあるディレクトリからの相対パスで、既定は `.`。`timeout` は秒単位で既定は 600 秒。`env` に環境変数を書ける。実行ツールが見つからない場合はコマンドとともに実行不可と表示する。実行ツールは利用者が事前に用意する。
- 数値の再現テストでは `seed` を `FUZUKUE_TEST_SEED` で渡す。スクリプトが乱数生成器に種を設定し、パッケージの版はプロジェクトで固定する。標準出力と `expect`（`cwd` からの相対パス）は JSON のキーと数値の組、`key,value` 形式の CSV、または `key=value` などのテキストを使う。各キーについて `|実測 − 期待値| ≤ max(abs_tol, rel_tol × |期待値|)` を確認する。既定の絶対許容誤差は `1e-8`、相対許容誤差は `1e-6`。

  ```toml
  [tests.reproduce]
  command = ["python3", "reproduce.py"]
  cwd = "analysis"
  timeout = 120
  seed = 42
  expect = "expected.json"
  abs_tol = 1e-8
  rel_tol = 1e-6

  [tests.reproduce.env]
  MODE = "paper"
  ```

- サイドバーの「その他」とスレッドの情報欄から「テスト」を開ける。各スイートはバックグラウンドで一つずつ実行され、停止と時間切れに対応する。標準出力と標準エラーは折りたたみ式で、直近の出力が更新される。失敗のファイル名・行番号を選ぶとソースエディタへ移動する。Cargo と pytest はランナーの集計を読み、件数を取得できない場合はコマンドの成否を 1 件として数える。
- MCP は `list_tests` と `run_tests` を提供する。`run_tests` は `suite` の省略で全スイートを実行し、成功・失敗の件数と最初の失敗箇所を返す。`filter` は Cargo・pytest・npm の引数にも反映し、すべてのコマンドに `FUZUKUE_TEST_FILTER` として渡す。作業役の指示には、コードを変更したときに関連するテストを実行し、失敗が残る間は完了と報告しないことを加えた。
- プロトコル 21 でテストの一覧・実行・停止と状態の配信を追加した。ソースエディタでは「中央に表示」と「右に戻す」で配置を切り替える。検索・置換は日本語で表示し、タブは「タブを閉じる」のツールチップが付いた × で閉じる。横スクロール中もガターは固定し、短い行に移ると左端を表示する。

### 段階 3 の実装

- ワークスペースごとに、言語とプロジェクトのルートを組にして言語サーバーを共有する。Rust は最寄りの Cargo パッケージを含む Cargo ワークスペース、Lean は最寄りの `lakefile.lean` または `lakefile.toml` のディレクトリを使う。ファイルを開くか、道具で問い合わせたときに標準入出力で起動する。5 分間使わなければ終了する。異常終了時はエディタに状態を表示し、開いているバッファーがあれば待ち時間を延ばしながら再起動する。
- ワークスペースまたは配下の `fuzukue.toml` に起動コマンドを置ける。引数はシェルを介さずに渡す。Rust と Lean にはプロジェクトと PATH 上のコマンドを検出した場合の既定値がある。ツールチェーンは利用者が事前に用意する。Elan の `lake` を使う場合は、ローカル情報から解決したインストール済みの実体を起動する。Python、R、Julia などは言語ごとのコマンドを設定する。

  ```toml
  [lsp]
  rust = "rust-analyzer"
  lean = "lake serve"
  ```

- プロトコル 36 でエディタの開閉・変更・保存と診断を同期し、問い合わせの結果を返す。関数などに絞った範囲編集でも、言語サーバーにはファイル全体を渡す。診断は本文とガターに出る。Ctrl+Space で補完を開き、F12 または Ctrl+クリックで定義のファイルと位置へ移る。Lean のホバーに戦術のゴールと期待される型を表示し、診断から `sorry` の警告やエラーを読める。
- 受付と作業役は `lsp_definition`、`lsp_references`、`lsp_hover`、`lsp_symbols`、`lsp_diagnostics`、`lsp_call_hierarchy`、`lean_goal` を使う。位置はワークスペース相対のパスと 1 始まりの行・UTF-16 列で渡す。名前から引くときは `symbol` でワークスペースの記号を検索する。同名の候補が複数あるときは位置を指定する。記号の一覧はファイルを指定するか、`query` でワークスペースを検索する。パスを含む結果はワークスペース内に絞る。呼び出し階層はサーバーが対応する場合に取得できる。
- 同じファイルを複数のクライアントで編集しているときは、各エディタからの問い合わせに先立って該当バッファーを同期する。道具からは最後に同期されたバッファーを参照し、診断は内容が一致するバッファーへ届ける。既存の記号索引との統合は段階 4 で行う。

## 順番

1. tree-sitter への切り替えとアウトライン、編集できるソースの画面（クライアントと、ファイルの保存）。実装は「段階 1 の実装」を参照。
2. テストの発見と実行（サーバー、道具、画面）。実装は「段階 2 の実装」を参照。
3. LSP の取り次ぎ。実装は「段階 3 の実装」を参照。
4. 記号の索引への統合と、データの流れのグラフ。
5. fuzukue 自身のビルドと入れ替え（[[self-update]]）。設定画面と MCP から開始できる。ビルド、テスト、指定した撮影と配布を通し、全ワークスペースの作業が終わってから入れ替える。起動確認に失敗したら直前のサーバーを起動する。
