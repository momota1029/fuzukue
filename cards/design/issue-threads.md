GitHub の Issue の活動をスレッドに紐づけ、その場で応対できるようにする。

## リポジトリごとの受付

1. リポジトリごとに受付スレッドを一つ指定する。スレッドメニューにリポジトリ名を出し、移動は確認を挟む。指定はスレッドに保存し、一覧に受付バッジを出す。
2. 指定中は新規 Issue・PR と追跡項目の更新が受付に集まる。本文の引用は外部資料として扱う。投稿者別の方針と書き込みの承認を使い、同じ項目の連続した更新は一つの受付ターンにまとめる。
3. Issue ごとのスレッドは、カードの操作か受付の道具で作業や議論を始めるときにだけ開く。作業スレッドから受付に戻れる。指定のないリポジトリは従来の自動作成を続ける。
4. 項目の状態はリポジトリごとに最大 128 件を保存する。受付にはその項目の要約と新着の抜粋を渡し、対応済み・見送り・要確認を記録できる。

## 既にあるもの

[[issue-queue]] と [[research-workshop]] は、ワークスペースの Issue と作業ブランチを表示する。リポジトリは `fuzukue.toml` の `[research].repo` か Git の `origin` から決まる。

GitHub は webhook を推奨する。secretaire は Tailscale の内側にあり、公開の受信先を持たないため、認証した定期取得を使う。取得先とクエリを固定し、`gh api -i` で `ETag` または `Last-Modified` を読み、次の取得で条件を送る。認証済みの `304 Not Modified` は一次レート制限に数えられない。サーバーは取得先ごとの `x-poll-interval` を守り、`retry-after` や一次制限のリセット時刻まで待つ。二次制限が続けば待ち時間を増やす。 [GitHub REST API の推奨事項](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

## 操作

- スレッド上部の「Issue に紐づける」で、開いている Issue、`#123`、Issue または PR の URL を指定する。複数を紐づけられる。チップに開閉状態、ラベル、PR の CI を表示し、押すと詳細を開く。詳細から紐づいたスレッドへ戻れる。
- Issue への着手、スレッドからの Issue 作成、Issue 用の作業ツリーでの委譲で紐づく。[[handoff]] の残作業を Issue にするときは、受付が承認を得た上で `create_handoff_issues` を使う。研究の入口カードを伴う場合は `research_issue_create` を使う。
- コメント、ラベルや状態の変更、レビューとそのコメント、CI の変化を会話に置く。一度に四件以上届いたときはまとめて折りたたむ。サイドバーには未読件数を出す。カードの「対応する」で、項目・本文・リンクを添えて、このスレッドの受付に一ターンを依頼する。複数の未読は「まとめて対応する」で一ターンに渡せる。「その他の操作」から「GitHub に返信」を開ける。差分へのコメントは元のレビューコメントのスレッドに返信する。長い本文は Markdown の抜粋を表示し、「全文」で展開する。
- スレッドと Issue の表示中は約 30 秒、その他は約 120 秒ごとに読む。受付の指定がなく、監視開始以降に開かれた Issue に紐づきがなければ作業スレッドを立て、本文を届ける。`[github].intake` は `all`（既定）、`dot`、`none` を選べる。指定がなく `all` または `dot` のときは、既存の `dot:*` Issue の更新も受け付ける。取得位置と更新の識別子はサーバー状態に残し、再起動時の二重通知を避ける。自分のコメントには隠し印を付け、ラベル操作は投稿者と変更内容を照合する。
- `github_issue_create` は利用者の承認を待ち、`[github].issue_repos` の許可一覧にある宛先に起票する。省略時の許可先は自分のリポジトリだけ。自分のリポジトリへの内部起票には `from-fuzukue` と `<!-- fuzukue -->` を付ける。このラベル付きの Issue ではスレッドも応対ターンも自動で開始しない。別リポジトリへの起票は、起票先の受付で扱えるよう、このラベルを付けずに行う。

## 投稿者の判定

- 「エージェントの報告」は報告用の Markdown 見出し（「やったこと」「分かったこと」「確かめたこと」「残り」や英語の同等表現）、隠し印、登録したログイン名、Bot の投稿、GitHub App 経由の投稿で判定する。同じアカウントを使う場合もこの判定を先に行う。
- 「あなた」はリポジトリ所有者または `gh api user` の認証アカウントからの更新。ほかの投稿者は `@login` で表示する。
- 利用者のアカウントを共有するエージェントは、`gh` での投稿にも `<!-- dot -->` や lab の `<!-- lab -->` など専用の隠し印を入れる。`fuzukue.toml` の `[github].agent_markers` で印の一覧を指定できる。省略時は `<!-- dot -->` と `<!-- fuzukue -->`。専用アカウントやアプリは `[github].agent_logins` にログイン名やアプリの名前・slug を追加できる。`<!-- fuzukue -->` は fuzukue 自身の投稿用。スレッド自身の書き込みとして照合できた場合は短い通知にし、それ以外は旧来の自分用の印とともに監視から除く。

## 応対

| 投稿者 | 既定の方針 |
| --- | --- |
| あなた | 受付が応対 |
| エージェントの報告 | 知らせるだけ |
| その他の投稿者 | 知らせるだけ |

- スレッドの情報欄で投稿者別に設定できる。「知らせるだけ」はカードと未読を更新する。最近のエージェント報告は次の受付ターンの文脈に入り、利用者が聞いたときに要約する。
- 「受付が応対」は空いたときに受付へ通知を渡す。受付は会話で答えるか、[[tiers]] の段階ルールで紐づく Issue の作業ツリーに委譲するか、利用者に訊く。投稿、ラベル変更、Issue のクローズ、取り込みには利用者の承認が要る。
- 「受付に任せる」は受付が該当項目への返信、ラベル変更、Issue のクローズを行える。新規 Issue の自動応対と指定先の受付スレッドの自動応対では、GitHub への書き込みに利用者の承認が要る。取り込みは通常のターンで [[branch-review]] の手順に従う。
- 外部エージェントへの連絡はリポジトリで使っている窓口を通す。受付は自分の作業役に委譲したり、利用者向けに返信案を作ったりできる。
- 手動の「対応する」はどの方針でも受付に渡す。GitHub への書き込みは選んだカードの方針に従う。複数選択時に利用者の承認を省けるのは、すべてが「受付に任せる」の場合に限る。
- 使用量やペースで休止している間、応対は待機する。自動応対はワークスペースの `[research].github_turns_per_hour` で一項目あたりに上限を設ける。既定は 3、0 で自動ターンを止める。上限を超えた更新も会話で読め、手動で対応を依頼できる。
- スレッドからの GitHub ツール操作と、紐づいた項目への書き込みが特定できる `gh` コマンドは、スレッドごとに記録する。所有者か認証アカウントの更新が記録した操作に一致すると、元のスレッドで短い通知にする。未読件数は増やさず、受付を起動しない。照合期間は `[github].echo_window_secs` で指定し、既定は 600 秒。
- 旧来の単一方針「知らせるだけ」は投稿者別の既定に移行する。「受付が応対」と「受付に任せる」は全投稿者に適用する設定として引き継ぐ。
