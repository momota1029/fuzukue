1. **合意済みの方針。** リリースを配布チャネルに置き、サーバーが自分で取得・検証して更新し、検証済みのクライアントを配る。
   作業状況を把握するサーバーが終了待ち・入れ替え・起動確認・復旧を担う。別端末のクライアントからサーバーを上書きする経路は設けず、接続先のプロトコルに適合する版を配る。
2. **リリースの作成。** CI でサーバー・Windows・Linux・Android の成果物と署名付きマニフェストを作る。版、完全なコミット SHA、プロトコル番号、各成果物の SHA-256、クライアント・サーバーそれぞれの最低互換プロトコルを記録する。
   公開リポジトリの成果物は認証なしで取得できるようにし、非公開フォーク向けに認証付きの取得経路も用意する。
   プロトコル番号とクライアントのクレートに変更がなく、クライアントに影響しないサーバー単独更新では、Windows を含むクライアントのビルドを省く。マニフェストに変更されたクライアント成果物を明記する。
3. **サーバーの自己更新。** [既存の自己更新](../../crates/secretaire/src/self_update.rs)に `release` モードを足し、ビルド工程をマニフェスト取得 → 署名とハッシュの検証 → ステージングに置き換える。
   点検、テスト・試運転、作業の終了待ち、入れ替え、起動確認、クライアント登録、失敗時のロールバックは [[self-update]] の流れを使う。ソースからのビルドと [Windows の事前ビルド・登録](../../scripts/publish-windows.sh)は開発・ドッグフード用に残す。
4. **クライアント配布。** サーバーは検証済みの成果物を保管し、起動確認後に[既存の配布処理](../../crates/secretaire/src/distribution.rs)で登録・通知する（[運用手順](../../docs/update.md)）。
5. **署名。** マニフェストに Ed25519（minisign 方式）の署名を付け、サーバーのバイナリまたは設定に固定した公開鍵で検証する。
   秘密鍵は公開時に利用者自身の端末で生成し、暗号化ファイルと CI シークレットに保管する。鍵の交代時は現行鍵で署名したマニフェストで次の公開鍵を告知できる。
   **鍵の生成・公開は利用者の明示指示待ち。**
6. **チャネル。** stable と beta を設け、nightly は必要に応じて後から追加する。Zed をモデルとし、毎週水曜に beta（Zed の Preview）を出し、beta で 1 週間検証した版を stable に昇格する。週の途中は重要な修正を cherry-pick してパッチを出す。版番号はこの周期に合わせて決める（例：`major.minor.patch` 形式で週次昇格ごとに minor を上げる）。[Zed のリリース方針](https://zed.dev/faq)
7. **Android。** 無料の配布経路を優先し、リリースの添付 APK をサイドロードする。更新は Obtainium のように新しい APK を確認・取得する流れとし、サーバーからも APK と [`android-latest.json`](../../android/README.md#リリースの作り方)を配る。
   Google Play は登録料が初回のみ 25 米ドルで、2023 年 11 月 13 日より後に作成された個人開発者アカウントでは、12 人以上が連続 14 日間オプトインしたクローズドテストを経て本番公開へのアクセスを申請する。Play は後から必要に応じて検討し、無料の F-Droid も候補とする。[登録料](https://support.google.com/googleplay/android-developer/answer/6112435)、[テスト要件](https://support.google.com/googleplay/android-developer/answer/14151465)
8. **ライセンス監査。** fuzukue 自作部分には MIT または Apache-2.0 を適用する。公開前に次の確認と対応を済ませる。
   1. `vendor/` の GPUI 系 3 クレートは Apache-2.0、`gpui-pdf` は MIT。Zed 本体や `collab`（旧版は AGPL）は GPL のため取り込まない。原著作権・ライセンス・該当する NOTICE を引き継ぎ、Apache-2.0 の変更ファイルには変更した旨を明記する。AOSP・Microsoft 由来のコードの表示も保つ。
   2. Rust の配布対象グラフに GPL／AGPL／LGPL 必須のクレートは見つからなかった。`self_cell` は Apache-2.0 を選択し、`option-ext`（MPL-2.0）のライセンスと対象ソースの入手先を同梱する。
   3. 配布物には Lucide／Feather、KaTeX フォント、Hayro 内のフォント・データの表示を含める。Linux は FreeType の同梱と表示を確認する。GPUI の例題のドラゴン画像は CC BY-SA 3.0。帰属を補い、由来不明の画像とドッグフード画像は権利確認か公開対象からの除外を行う。
   4. Android はリリースの添付 APK を使う。KaTeX フォント（OFL-1.1）と OkHttp の Public Suffix List（MPL-2.0）を含め、署名済み APK の依存・ネイティブライブラリ・表示を照合する。今回は既存の debug APK まで確認した。
   5. 外部資料、引用、参考実装の再配布条件を確認する。公開用の例には再配布できる資料を使用する。
   6. ソースには `LICENSE-MIT`、`LICENSE-APACHE`、`NOTICE`、`THIRD_PARTY_NOTICES` を置く。バイナリ配布時は、その配布物に入る依存の表示とライセンス全文を作成する。
9. **公開前の確認。** リポジトリを公開する方針は合意済み。実際の公開は利用者の別途明示の指示を受けて行う。
   - Git 履歴の秘密情報・トークン・個人のパス・メールアドレスと、`fuzukue.toml` の Git 除外を確認する。非公開の `threads/`・`inbox/` の記録を除去または移設する。
   - GitHub の Issue テンプレート、`from-fuzukue` などのラベル、ブランチ保護を確認する。OAuth Client ID は公開情報であり、文書に秘密情報がないことを確認する。
10. **残件。** ライセンスの最終確認、版番号形式の詳細、F-Droid／Google Play の採否、公開の実施。

11. **公開前監査結果（2026-11-23）。** Android β は配布専用の公開リポジトリを使い、署名付き APK・SHA-256・更新 JSON をプレリリースに添付する案を推奨する。検査した APK の署名とハッシュは一致し、既知の認証情報の形式には一致しなかった。KaTeX・RaTeX・Public Suffix List の表示と対応ソースの案内を整えてから配布する。β の更新先にはタグを固定した HTTPS URL を使う。
    本体の履歴にはコミットのメールアドレス、会話記録、研究メモ・引き継ぎ、端末情報が含まれる。本体は非公開を維持し、ソースを公開する場合は、権利と内容を確認したスナップショットを新規リポジトリに出す案を優先する。
