2026-11-24 の利用者判断。「承認待ちで止まること自体がおかしい」。利用者が離席していても、調査、下書き、許可済みの検証など、その時点でできる最小限の仕事を進める。判断が要る操作は取り消せる依頼として積み、許可されれば実行候補に戻す。判断ボタンはデスクトップと Android の会話下端、入力欄のすぐ上に固定する。ファイル、Git、テスト、シェルなどの基本操作は fuzukue の MCP を通す。以下は実装前の設計案。

## 現状と流用する部品

| 部品 | 現在の動作 |

## A. 非同期の承認

### 承認オブジェクト

- サーバーが `approval_id` を発行し、ワークスペース、スレッド、ジョブ、依頼者、リスク区分（低・中・高）、無人時の扱い、理由、作成・期限・更新時刻、状態、許可の範囲を永続化する。会話イベントはこの状態を配信する。決定の正本はサーバーに置き、クライアントは再接続時に保留キューとその後の更新を突き合わせる。
- 対象は正規化した `action = {tool, args, scope}`。ツールごとの型で引数と既定値を確定し、`scope` に実行主体、チェックアウトの識別子、基準ディレクトリ、パス・アクセス種別や通信先、必要な事前条件を含める。シェル本文はシェルの意味を変える整形をせず、実行するバイト列を確定する。ファイル変更は変更前後のハッシュ、Git コミットは対象パス・差分・インデックスの状態と `HEAD` を判断対象に含める。表示にはマスクした引数と差分を使い、再試行に必要な内容はアクセス制御された記録に置く。
- 同一の所有者・スレッド・ジョブの同一操作と事前条件には、保留中の ID を再利用する。判定と登録を一つの更新にし、連打や並列呼び出しでも依頼・通知は一件にする。フォルダー許可などスレッド単位の能力だけは、ジョブをまたいだ重複排除を明示する。差分、対象、リスク、要求する権限が変われば別の依頼にする。
- `pending` から `granted`、`denied`、`withdrawn`、`expired` に移る。許可の既定は **一回限り**（一つの操作の実行権を原子的に消費）。**範囲指定**は表示されたワークスペース・パス集合・操作種別などに限定し、**期限付き**は指定時刻まで同じ制約で再利用できる。回数・範囲・期限は併用でき、明示した承認から広げない。新設する範囲指定の許可には有限の期限を設ける。
- 依頼者または権限のある利用者は、保留中の依頼を撤回できる。期限切れ、拒否、撤回では実行候補を作らない。許可後も未着手の実行権は取り消せ、期限切れで失効する。実行権の取得と失効の競合はサーバーで直列化する。着手済みの実行は個別のキャンセル経路で止め、発生した副作用を記録する。ジョブの通常終了は依頼を残し、利用者によるジョブ中止やスレッドのアーカイブは関連する未着手の依頼・実行権を撤回する。
- 依頼、重複、判断者と判断理由、使用した規則と方針版、撤回・失効、実行権の消費、実行結果を ID で追えるようにする。判断の履歴は追記し、使用済みの許可も履歴から読める。コマンド全体や環境変数値など秘密を含み得る情報は会話・通知・朝の報告に転載しない。

### MCP の応答と再開

承認が要る場合は登録後、次の形を直ちに返す。人間や `advisor` の返答を待つ Future を MCP 呼び出しに残さない。`pending` は受理を示し、操作にはまだ着手していない。引数の不備や許可不能な対象は、承認キューに積む前にエラーで返す。

```json
{
  "status": "pending",
  "approval_id": "apr_example",
  "what_to_do_next": {
    "continue": "Run independent steps or save a partial result.",
    "retry": "Retry the same action after the approval notification."
  }
}
```

必要な手順だけを計画上の支障として結び、受付・作業役は残りを進める。同じ呼び出しをポーリングせず、使える資料で調査する、ローカルに下書きする、許可済みのチェックで検証するなど、依存しない成果を残す。別作業が尽きたら部分成果、未完了の手順、再開条件を保存してターンと作業枠を返す。最後の手順が承認待ちでも目標全体を完了扱いにしない。

1. **既定は通知して再試行。** `granted` を永続化してから、稼働中のエージェントへ既存の指示注入経路で ID と次の操作を通知する。再試行は `approval_id` と同じ操作を渡し、現在の権限、対象、ハッシュや `HEAD` を照合してから実行する。条件が変わった場合は古い実行権を無効にし、読み直しと必要に応じた新規依頼を案内する。`fs_write`、`git_commit_scoped`、任意シェルはこの方式から始める。
2. **登録済みの冪等な操作はサーバー実行も選べる。** たとえば、同じ ID と絶対の失効時刻でフォルダー読み取り許可を登録する処理。許可イベントと再開用の記録を一貫して保存し、実行前に権限・対象を再検査する。同じ ID を冪等キーとして再配信し、結果を記録して通知する。対象ツールが冪等性と結果照会を保証できる場合に限る。
3. **ジョブが終了していたら継続ジョブを積む。** held-work の永続キューと claim を流用し、元ジョブ、計画手順、チェックポイント、操作 ID、権限の参照を持つ継続ジョブを一件だけ作る。実行中通知と終了処理が競合しても、同じ ID の通知受領か継続ジョブのどちらかに引き継ぐ。チェックアウトは期限付きで保持し、消失や世代変更があれば安全に再構成できる範囲を確認する。実行結果が不明な中断は監査と作業状態を照合してから扱う。中止、アーカイブ、取り消し、期限切れの後は残ったキューから起動しない。

### 夜間の方針

ワークスペースごとに、サーバー管理の `night-shift.toml` を設ける案。利用者が有効時間帯・タイムゾーン、対象ワークスペースと役割、`touches` 内の対象パス、許可するツール・レシピ・通信先、実行時間・モデル使用量・同時ジョブ数・試行回数・保留件数の上限を設定する。時間帯終了、予算切れ、連続失敗、方針変更、利用者の停止操作で該当する新規実行を止め、必要なチェックポイントを残す。方針ファイルの不備や設定のない操作は自動許可しない。作業役にはこのファイルの変更権限を与えない。

| 区分 | 無人時の扱い |
| --- | --- |
| `auto` | 検査済みの読み取り、`touches` 内の構造化編集、明示したレシピなどを、設定の範囲と予算内で進める。検査の済んだローカルコミットを含める場合は別途明示する。 |
| `defer-and-continue` | 作業ツリー内の範囲外編集、追加の読み取り許可、分類できないシェルや許可範囲を広げる通信、GitHub の返信・ラベル変更・起票・クローズなどは保留に積む。依存する操作だけを止め、独立作業を続ける。 |
| `never-unattended` | push、publish、release、永続データの削除、署名、GitHub のリポジトリ作成・改名・公開範囲変更・削除、ブランチや ref の変更、リポジトリ設定の変更、自己更新のバイナリー入れ替え、認証・名前／識別情報の変更は、無人枠から実行しない。起きている利用者が対象を確認し、通常の対話枠で個別に判断する。人間専用の操作は利用者の操作経路を使う。 |

制約はサーバーで強制する。任意シェルは全副作用を静的に分類できないため、無人枠には構造化 MCP、検査済みの読み取りコマンド、登録済みレシピだけを出す。優先順位は人間専用・禁止事項、現在の対象と実行環境の制約、利用者の明示判断、無人方針の順とする。`advisor` は対象の審査に時間上限を設け、人間専用操作の許可や実行範囲の拡大を行わない。朝のまとめは、完了と部分成果へのリンク、残った承認（ID・理由・期限）、拒否や失効、停止原因と試験結果、予算消費をスレッドごとにまとめて届ける。

### 会話下端の承認ドック

- 会話のスクロール領域の外、入力欄のすぐ上に保留件数と先頭の依頼を固定する。伸ばせる領域に高さの上限を設け、件数が多ければドック内でスクロールする。選択中のスレッドの依頼をジョブでまとめ、同じグループ内では到着順に並べる。別スレッドの依頼は一覧バッジと通知から開く。
- 行には操作名、対象・範囲、理由、リスク、期限、許可と拒否を置く。展開すると引数、差分、依頼元、許可の有効範囲を読める。低・中・高は、中立色・黄系・赤系と文字ラベルで識別する。選択した同種・同範囲の依頼には一括許可と一括拒否を出し、対象と範囲を確定前に読み返せるようにする。`never-unattended` を含む高リスクの許可は個別操作に限る。競合で先に決まった項目があれば一括操作の結果に出す。
- デスクトップでは `Tab` / `Shift+Tab` で移動し、フォーカス中のボタンを `Enter` / `Space` で操作し、`Esc` で詳細を閉じて元の位置に戻る。依頼が増えても入力のフォーカスを奪わない。Android は狭い画面で件数と先頭の依頼を表示し、入力欄の上から展開する。IME やシステムバーの余白を考慮し、タップ領域と読み上げを確保する。状態、判断範囲・期限、一括操作、再接続時の挙動は両端末で揃える。
- 新規保留は表示中の通知抑制・スレッドのミュートを尊重して知らせる。同じ ID は再通知せず、多い場合はまとめる。OS 通知から該当スレッドの依頼を開く。解決済みの行はドックから外れ、許可・拒否・撤回・期限切れと判断者を短い会話イベントに残す。元の操作と最終結果をたどれ、会話と一緒にスクロールして退く。判断が済んでも、実行結果が出るまでは実行済みと表示しない。

## B. 基本操作を fuzukue MCP に揃える

ファイルの読み取り、検索、書き込み、差分適用、Git の照会と範囲内コミット、テスト・撮影の定型作業は専用 MCP に揃える。定型外のビルドや調査には `exec` を加える。専用ツールと `exec` は同じジョブの権限と承認オブジェクトを参照する。`exec` で構造化ツールの保護対象や権限外の操作へ迂回できないようにする。

### exec の契約

| 入力 | 内容 |
| --- | --- |
| `command` | Bash に渡すコマンド文字列。非ログイン・非対話、初期化ファイルなし。入力の長さに上限を設ける。 |
| `cwd` | ジョブ専用クローンからの相対パス。既定はクローンの根。正規化・実在確認後にクローン内のディレクトリを保持して起動し、リンクや入れ替えで外へ出ないことを実行直前にも確かめる。 |
| `timeout_ms` | ジョブ予算内の上限付き実行時間。タイムアウト・取り消し・サーバー停止時は、実行単位のプロセス群を回収する。 |
| `env` | `LANG` など、サーバーが名前と値の形式を認めた変数だけ。環境は空から組み立て、実行ファイルの `PATH` と一時・ホーム・設定領域はサーバーが指定する。認証情報、プロキシ設定、ローダーやシェル初期化を変更する変数は渡さない。 |
| `background` | 既定は `false`。`true` は承認・投入後に `exec_job_id` を返し、`exec_poll`、`exec_cancel`、`exec_stream` で状態の照会、取り消し、カーソル付きログ取得を行う。いずれも同じ実行主体とスレッド／ジョブの権限で検証する。 |

承認待ちは `background` にかかわらず先に `pending` と `approval_id` を返す。許可済みの短いフォアグラウンド実行は、`status`、`exit_code`（終了コードが取れない時は `null`）、`stdout`、`stderr`、`duration_ms` を返す。起動失敗、シグナル、タイムアウト、取り消しを区別し、出力はストリームごとにバイト上限、切り詰めマーカー、`truncated` を持たせる。長い出力は上限付きのジョブ用ログへ流し、子プロセスのパイプを詰まらせない。文字列は UTF-8 とし、不正バイトの置換を明示する。必要な生バイトは権限と保持期限のあるログで扱う。バックグラウンド実行も同じ形式で終了結果を取得でき、再接続でカーソルから追える。サーバーを再起動した後に結果が確定できない実行は中断として記録し、自動再実行しない。

ジョブごとに所有権と権限を確認した専用ディレクトリを作り、`TMPDIR`、`TMP`、`TEMP`、`HOME`、`XDG_CONFIG_HOME`、`XDG_CACHE_HOME`、`XDG_DATA_HOME`、`XDG_STATE_HOME`、`XDG_RUNTIME_DIR` を配下に用意する。ホストの `/tmp` や利用者のホームを前提にせず、`unable to make temporary file` や `/tmp` 不在を回避する。隔離環境で `/tmp` を直に使うプログラムにはジョブの一時領域をそこにマウントする。ツールチェーンと依存キャッシュは必要なものだけ読み取り専用で提供し、ビルドの一時生成物はジョブ領域へ逃がす。

### 分類と OS 隔離

- 読み取り専用の自動分類の候補は `ls`、`cat`、`head`、`tail`、`wc`、`grep`、`rg`、`find`（`-exec`・`-delete` なし）、`sed -n`（`-i` と `w` コマンドなし）、`awk`（`system()` と出力リダイレクトなし）、`sort`、`uniq`、`diff`、`stat`、`file`、`du`、`df`、`pwd`、`echo`。既存 Bash 検査の構文・引数・パス検証を流用し、固定した実行ファイルと、読み取り専用と判定できる引数の組だけを自動で許可する。
- 基本は `cwd` を使う。`cd X && …` も、移動先がクローン内で、後続の `&&` やパイプを含む全段を移動先から検査してすべて読み取り専用と判定できれば、自動許可の対象とする。未知のフラグ、リダイレクト、展開、置換、読み取り専用と判定できないスクリプトは保留に回す。
- Git の `status`、`log`、`diff` などは、既存の `git_read` の許可形式と安全な実行設定を使えるものだけ自動許可候補とする。外部 diff・textconv・ページャー・任意の設定差し替え・インデックス更新を伴う形式は外す。`cargo check` は `target` に書き込み、`build.rs` や手続きマクロを実行し得るので、読み取り扱いには入れない。既定は保留、定型化できたものは隔離済みレシピと無人方針で扱う。読み取りとして検査できない実行は保留にし、禁止対象は拒否または人間専用経路に回す。
- Linux ではサーバーが bubblewrap で最小限のファイルシステム、ユーザー・マウント・PID・ネットワークの名前空間を組み立てる。書き込み可能なルートは、ジョブ専用の作業領域とクローン内で `touches` が許す領域に限定する。クローン全体は読み取り専用を基準とし、その上に許可済みの書き込み先だけを載せる。読み取りコマンドにはクローンへの書き込み先を載せない。任意の glob や単一ファイルの作成・原子的置換のために親ディレクトリ全体を開ける必要がある場合は、ジョブの一時領域で生成し、厳密なパス検査を持つファイル MCP で反映する。共有ツリー、Git の内部、サービス状態、ホストのホーム、認証ソケットは書き込み境界から除外し、実行に不要なものは見せない。 [bubblewrap の隔離モデル](https://github.com/containers/bubblewrap/blob/main/README.md#sandboxing)
- 外部通信は既定で無効。追加する場合は接続先・ポート・期間を表示し、サーバーの許可リストと個別承認が要求する条件を満たす経路だけを、出口制限を強制するプロキシ等で開ける。子プロセスにも制限を継承し、名前解決やリダイレクトで許可範囲が広がらないようにする。ホストのソケットやネットワーク全体を渡さない。撮影などでループバックが必要な場合は名前付きレシピ側で隔離条件を定義する。
- 現行のスコープ付き Codex 作業役はネイティブの許可プロファイルでクローン・一時領域の権限を設定し、ネットワークと昇格要求を止めている。通常の書き込みモードはクローン単位で、厳密な `touches` 検査は MCP が担う。Claude Bash の検査とフックはツール判断で、現行の作業役起動は Bash の OS 隔離を設定していない。WSL2 の試行は依存とユーザー名前空間の存在を確認した段階で、bubblewrap のマウント試行は失敗している。サービス実行アカウントで起動と境界を確かめ、利用できない環境では汎用 `exec` を停止する。 [Codex 起動](../../crates/secretaire/src/codex.rs) · [Claude 起動](../../crates/secretaire/src/claude.rs)

### ネイティブツールからの移行

1. まず両経路の利用を計測する。役割・バックエンドごとに MCP 選択率、独立作業の進行、承認件数、成功率、再試行、所要時間を、変更の小さい実務タスクで比較する。コマンド本文や機微な引数の収集は避ける。
2. 同じタスクを MCP 優先で実行する。ファイルの範囲編集、検索、Git、ビルド、ログ取得をタスクに含め、ツール説明・例・エラーに次の操作を示す。モデルが学習済みのネイティブ操作を外すと成功率が落ちることがあるため、選択ミスと実行自体の失敗を分けて扱い、役割単位で段階的に切り替える。
3. Claude は既存の `--tools` 選択に加え、`--disallowedTools` で `Bash`、`Edit`、`Write` と同系の編集・読み取りツールを役割ごとに外す。Codex は役割ごとの read-only の `sandbox`／名前付きプロファイルと `approval_policy = "never"` で、ネイティブのシェル・`apply_patch` からの書き込みと許可昇格を閉じる。シェルの表示・呼び出しは `features.shell_tool = false` の候補を対象版で検証する。`apply_patch` の非表示が可能かは別途確認し、設定で制御できない版では読取専用の封じ込めを検証したうえで、ネイティブツール廃止の完了判定を保留する。MCP の側で認証・権限を別に強制する。 [Claude CLI](https://code.claude.com/docs/en/cli-reference) · [Codex 設定](https://learn.chatgpt.com/docs/config-file/config-reference)
4. 残るネイティブ承認は移行中の互換経路として明示する。バックエンドが `pending` を表現できず、その RPC を保留するとターンが止まる場合は、呼び出しを速やかに拒否し、同じ操作を MCP で依頼できる案内を返す。ネイティブ承認を許可して隔離なしで再試行する経路は設けない。

初期 `exec` は stdin を閉じた非対話実行とし、PTY、対話認証、エディターは対象外とする。必要性が確認できたら独立の権限を持つ実行形態として検討する。長時間処理はバックグラウンドと上限・取り消しで扱う。Windows ホストは同等の隔離が確認できるまで構造化 MCP と対応済みレシピを使い、Linux/WSL のサーバーに接続する Windows・Android クライアントからも同じ承認を操作できるようにする。

## 実装の順序と完了条件

1. **承認オブジェクト、キュー、ドック。** サーバーの保存・再配信とクライアント双方の固定表示を入れる。同一操作の並行登録、再起動・再接続、両端末から異なる判断が届く競合、期限切れ・取り消しを試し、判断と履歴が一件に収束することを確認する。デスクトップは `scripts/shot.sh` でスクロール・多数の保留・解決後を撮り、Android は同じ場面に加えて実機で IME 表示中と通知からの遷移を確認する。
2. **既存 MCP の即時応答。** `fs_write` と同系ツールの範囲外、フォルダー依頼、`git_commit_scoped` の範囲拡大を共通契約へ移す。コミットは以前から許可された `touches` の範囲を守り、拡大はクローン内で許せる対象のみに限定する。利用者が応答しないテストで `pending` の直後に別の MCP が成功し、変更・コミットが発生しないことを確認する。変更済みのファイル・フォルダー・`HEAD` への古い許可と、保護パスは拒否する。
3. **許可から再開、夜間方針。** 稼働中には通知し、終了後は held-work から一件だけ継続する。二重通知、完了と許可の競合、再起動、消費直前の失効、再試行の結果不明を試す。応答なしの無人枠で部分成果と朝のまとめが残り、予算切れや人間専用操作が実行開始を防ぐことを確認する。
4. **bubblewrap 導入前の `exec` 試作。** 隔離なしの段階は、開発者が有効にした使い捨ての検証環境と固定フィクスチャに限る。全件一回限りの承認を要し、通常ジョブや無人枠には公開しない。`pending` 中にプロセスが起きないこと、専用一時領域、終了コード、文字化けと切り詰め、タイムアウト、バックグラウンドの照会・ログ・取り消しを確認する。
5. **bubblewrap と分類器。** 実際のサービスアカウントで Linux と WSL2 のマウント検査を行う。読み取り・許可済みビルドの成功、`touches` 外や保護領域への書き込み拒否、リンクと後続プロセスの制限、無許可通信の遮断、許可先に限る通信、隔離の起動失敗時に実行されないことを確かめてから汎用 `exec` を公開する。
6. **役割ごとのネイティブツール廃止。** 同じ課題で Claude と Codex を比較し、合意した成功率・所要時間の基準を満たした役割から無効化する。変更とビルドを MCP だけで終えられ、ネイティブからの編集・シェルが方針を迂回せず、利用者不在でも最低限の成果が残ることを確認する。

### サーバーの承認キュー（R-59）

- `Welcome` の `approval_queue: true` がキュー API の利用可を示す。クライアントは接続し、対象ワークスペースを選んだ後、毎回 `list_pending_approvals` を送る。`approval_queue` イベントの `result.Ok` でローカルの保留一覧を置き換え、それ以後の `approval_queue_changed` を ID ごとに反映する。再接続とワークスペース切り替えでも同じ手順で購読し、更新の取りこぼしで切断された場合も一覧から復元する。
- 許可・拒否・撤回は `decide_approval` を送る。`approval_decision_result` の `request` は呼び出しと対応し、先に決まった項目への判断はエラーになる。期限は Unix ミリ秒で表し、一回限りの許可には依頼の期限を使う。範囲指定と期限付きの許可には有効期限を指定する。
- 状態と追記履歴はワークスペースの状態ディレクトリーの `async-approvals.json` に原子的に保存する。生の引数と実行範囲はサーバー内に保存し、キューの応答は登録時に渡された表示用の値を使う。消費には同じ所有者と正規化済み操作が要る。

## 未決事項

- 承認、判断履歴、継続ジョブを同じストアに置くか。既存 held-work との書き込みをどの境界で一貫させ、自己更新でロールバックした場合にどう扱うか。
- 保留・許可・ログ・クローンの既定保持期限と上限。長い保留の再通知、アーカイブからの再開、既存フォルダー許可と Bash 接頭辞規則の移行範囲。
- 一括許可の対象にする操作、役割ごとの夜間予算、MCP 優先へ切り替える成功率と所要時間の基準。
- 正確な `touches` のマウント表現、ジョブ専用差分を反映する方式、キャッシュや限定通信の提供方法。Windows ホストの隔離、PTY と非 UTF-8 の必要範囲。
