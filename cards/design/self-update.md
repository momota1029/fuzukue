Linux / WSL のサーバーを設定画面から更新できるようにする。

## 計画終了・更新の作業保全

通常の終了、更新、試運転の昇格、ロールバックでは、サーバーが全ワークスペースの稼働を確認する。実行中のターン、作業役、追跡中のコマンドやレシピ、承認待ち、使用量による一時停止、実行可能な入力などがあれば、理由と件数を返す。アーカイブ済みの保管入力は保持し、使用量の再開タイマーやメモリ上の待ち行列に残る作業はアーカイブ後も稼働として数える。受付の MCP から要求した更新では、ターン入力で発行した証明を照合し、認証済みのその一回のターンだけを受付時と切り替え待ちの判定から除外する。切り替え前にそのターンの終了を待つ。準備は候補の作業領域で行い、切り替え前に再検査して新規作業の受付を閉じる。期限までに終了や保存を確認できなければ更新を中止する。強制中断には明示操作が必要となる。

後続段階に向けて次の判断を採用する。

- 最初の更新は外部の起動管理で停止を確認してから切り替える。起動に失敗して対応版が使えない間は停止状態を維持する。初回失敗時の隔離閲覧は提供しない。
- 再起動後に届いた新規外部イベントの自動処理は、受付が状況を報告し、利用者が了承してから再開する。
- 強制終了時の引き継ぎは全体で 2 分待つ。元のセッションを開けない場合は、別の作業役が履歴を読み取り専用で調べられる。確認できない結果は未完了として残す。
- 受付は確認済みの作業を再開できる。外部への書き込みは改めて利用者に確認する。

## 設定と操作

`<repo>/target/release/secretaire` から起動していて `<repo>/Cargo.toml` が fuzukue のワークスペースなら、そのチェックアウトをソースとする。場所を指定するときは `~/.config/fuzukue/server.toml` に書く。サーバーが開くプロジェクト（例 `~/research`）は、従来どおり起動時の引数で指定する。

```toml
[self_update]
source = "~/fuzukue"
branch = "main"
tests = ["cargo test --locked -p secretaire -p fuzukue-proto -p fuzukue-view -p fuzukue-i18n -p fuzukue-cards"]
shots = [["scripts/shot.sh", "examples/lab", "tests/shots/self-update.json"]]
# Windows クライアントも作る WSL では次の行を加える。
# publish = ["scripts/publish-windows.sh"]
```

`branch` の既定は `main`。既定では上のテストを走らせ、撮影と配布は設定した場合に実行する。コマンドはソースのチェックアウトを作業ディレクトリとして実行する。配列は実行ファイルと引数、文字列は `sh -c` に渡すコマンド。`FUZUKUE_PROJECT_DIR` は起動時のプロジェクト、`FUZUKUE_SERVER_BINARY` はステージ済みの実行ファイルを指す。配布スクリプトはその実行ファイルでクライアントを登録する。配布先は [[distribution]] の経路を使う。

設定の「接続」にある「サーバーを更新」で稼働中のビルド ID、ソースのコミット、工程ごとの状態とログを見られる。「ビルドして入れ替える」で開始する。受付の MCP 道具 `self_update` では `{"action":"status"}` で状況を読み、利用者の明示の了承を得てから `{"action":"start","confirm":true}` で開始する。

## ビルドと入れ替え

1. ソースが指定ブランチにあり、作業ツリーがきれいで、コミットが稼働中の版と異なることを確かめる。`threads/` の会話の記録と `inbox/` の添付はワークスペースのデータなので、作業ツリーの点検から外す。同じコミットの一時チェックアウトで以降の工程を走らせる。
2. 別の Cargo ターゲットにリリース版をビルドする。実行ファイルを `$XDG_STATE_HOME/fuzukue/server-builds/<commit>/build-*/secretaire` に控え、テストと撮影を順に行う。設定済みの Windows クライアントの事前ビルドは点検直後から並行して進める。状態ディレクトリの既定は `~/.local/state`。失敗した工程で止まり、各工程の末尾のログを画面に残す。
3. 開いている全ワークスペースのターンとジョブが終わるのを待つ。作業開始を閉じてから「サーバーを入れ替えます」と知らせ、待ち受けを閉じる。セッション ID、スレッド、会話のタイムラインと作業ログ、ワークスペーステストの直近結果は同じ状態ディレクトリから読み戻す。
4. 別セッションの `secretaire self-swap` が旧プロセスの終了を待つ。起動引数、作業ディレクトリ、環境を引き継ぎ、新版が元の設定に従って待ち受けを張り直す。監督はループバックの HTTP 応答が起動したプロセスのものかを最長 30 秒間確かめる。クライアントは同じ接続先に再接続する。
5. 監督が起動確認と `server-builds/current`・`previous` の切り替えを確定する。失敗した場合は確認用のプロセスを終了し、直前の実行ファイルを起動する。「前の版に戻す」もターンとジョブの終了を待ち、同じ起動確認を行う。
6. 起動確認が通った新版だけが、保存済みのクライアントを登録し、配布マニフェストの更新後に接続中の端末に通知する。登録に失敗した場合は配布工程に理由を表示し、同じサーバー版の次回起動時に保存した工程から再試行する。

停止後に入れ替えた版を手動で起動するときは `server-builds/current` を実行し、通常のプロジェクト引数を渡す。ソースは `server.toml` で指定する。

プロトコル 35 で更新の状態、工程ログ、入れ替え通知を配信する。クライアントの更新通知とダウンロードは既存の配布経路を使う。

## Draining の設計

従来の設計の待機画面と 54 番の監査を起点にした追加仕様。以下の状態名は自己更新の工程と `WaitControl` の遷移を表す。

| 状態 | 既存の工程との対応と遷移条件 |
| --- | --- |
| Running | 通常運転。サーバー更新の開始で Preparing に入る。手動の「前の版に戻す」は復帰先の実行ファイルを点検し、同じ Draining に入る。クライアント単独の更新中も通常運転を続ける。 |
| Preparing | 点検・取得・ビルド・テスト・設定済みの撮影やクライアントの事前ビルドを通し、入れ替えに使う実行ファイルを確定する。この間は本番の受付、利用者の依頼による委譲、監視を通常どおり動かす。方針役の自動委譲と計画確認は既定で保留する。別ポートの試運転と昇格承認待ちも本番の通常運転を続け、昇格に必要な準備が通ってから Draining に入る。準備の失敗や試運転の破棄は Running に戻る。 |
| Draining | `Step::Wait` の開始時に `WaitControl` と既存の作業開始ゲートで全ワークスペースの新規開始を閉じる。通常の操作では稼働を再検査し、要求元のターンが残っていればその終了を待つ。中止が先に確定すれば同じ稼働版で Running に戻る。 |
| Ready | 開始済みのターン・作業役・裏の仕事が終了し、成果・再開記録・保留入力の保存が済み、`swap_gate` の排他を得た状態。アーカイブ済みの保管入力は待機を延ばさない。新規開始を閉じたまま `Step::Wait` を完了する。 |
| Swapping | `Step::Swap` と既存の `self-swap`／systemd の監督処理で待ち受けと実行ファイルを切り替える。起動確認中の `trial_pending` でも開始を閉じ、監督が対象プロセスの正常起動と切り替え結果を確定してから、新版が保留を読み直して Running に戻る。 |
| Recovery → Running | 起動確認に失敗したら監督が新版を終了させ、直前の稼働版を起動する。旧版の起動確認と復帰結果の確定後に同じ保留を読み直す。復帰にも失敗したときはエラーと回収先を残し、保留を保持する。 |

`WaitControl` は理由（`Update`／`Shutdown`）を持つ。クライアントの `RequestDrain` は稼働中なら拒否し、保存できたときに Ready へ進む。SIGTERM・SIGINT、`secretaire service stop`、systemd の停止では退勤指示と保存を行い、Ready または `[shutdown].drain_seconds`（既定 60 秒）で終了する。二度目のシグナルは直ちに終了する。クライアントから開始した停止は確定前に `CancelDrain` で取り消せる。`DrainStatus` は理由、段階、実行中の件数、待機の対象と理由を返す。自己更新の既存の状態と操作も引き続き使う。

### 開始と保留

`Update::admit`／`Workspace::admit_work` の判定と開始済みへの登録を、Draining への遷移と競合しないようにする。受理やタスク生成の後にスロットやターンを待つ経路でも、実行開始時に判定する。判定を通った処理は終了と保存まで待機理由に載せる。開始前の待ち行列は開始許可を保持せず、保留の保存後に排他の取得を妨げない。WebSocket と MCP の入口では操作ごとに開始可否を判定し、状態の閲覧や既存作業を終えるための操作を通す。

| 対象 | Draining 以降の扱い | 再開条件 |
| --- | --- | --- |
| 手動の委譲・開始 | 新しい `delegate`（子への委譲を含む）、ワンショット、引き継ぎの実行、Issue 作業開始、手動 `plan`／`replan` は更新待ちを理由に受付エラーを返す。すでに受理したスロット待ちの委譲は受付済み依頼として保留する。 | 受理前に止めた操作は Running に戻ってから利用者か呼び出し元が明示的に再試行する。 |
| 受付済み依頼・報告 | Claude の入力待ち、委譲のスロット待ち、`deliver_desk` の依頼・作業報告などを保存する。受理を返した入力には ID・ワークスペース・スレッド・本文と添付参照・順序を残す。Draining 中に既存スレッドへの入力を受け付けるときも、保存後に保留として応答する。保存できない入力には受付エラーを返す。退勤報告は既存の履歴に残し、報告配送のために受付の新規ターンが要る場合は配送を保留する。 | Running に戻ってから、同じスレッドで元の順序と承認・権限を守って配送する。終了済みの質問や無効になった依頼は理由を記録し、判断が必要なものは確認待ちにする。 |
| 自動継続 | `resume_goal`、`plan_follow_up`、使用量リセットや「今すぐ再開」、自動再計画・再試行、受付の追加入力による新規ターンを止める。完了結果と計画の更新に必要な材料を保存する。同じ目標の継続通知はまとめる。 | Running に戻ったときに保存した最新の計画・結果を読み、目標が有効で使用枠と依存条件を満たす場合だけ次の手順を一度開始する。使用量休止・利用者の停止・承認待ちはそれぞれの解除条件を保つ。 |
| 監視イベント・自動処理 | `watch` と GitHub/Issue 監視の新規ポーリングと受付呼び出しを止める。取得済みのイベントは既存の outbox・カーソル・スレッドの記録を使って保存し、受付起動の保留を配送済みにしない。自動ビルド・査読・差分確認のための変化は再走査できるように残す。 | Running に戻ったら保存済みカーソルから監視を再開する。イベント ID と配信済みの記録を照合し、監視設定、通知間隔、上限と承認条件を再評価する。自動ビルドなどは現在の入力と設定から必要な処理を起こす。クライアント接続の有無にかかわらず同じ条件で再開する。 |

### 退勤と復帰

- 待機の対象は、応答を受け取れる承認要求に限る。再起動、作業の中断、Claude 側の要求取消で応答先を失った承認は直ちに取り消し、決着を履歴に残す。稼働中に残った応答先のない要求の失効には `[self_update].orphan_approval_seconds`（既定 600 秒）を使う。
- 単独の Git Push／Pull と研究 Issue の作成・ready 化・取り込みは、要求から結果の記録まで開始許可を保持する。承認応答の処理が Draining の開始より先なら、ロック待ちと後続のコマンドを含めて実行期限 180 秒で完了を待つ。承認待ちには実行期限を適用せず、Draining が始まった後の承認には再要求を案内する。待機を中止して稼働に戻った場合も新しい承認を求める。
- 強制操作と停止期限では未回答の承認を取り消し、承認後に中断した操作は確認待ちとして保存する。`gh` の呼び出しには既定 120 秒の期限を設ける（`FUZUKUE_GH_TIMEOUT_SECONDS`）。研究 Issue の取り込みはローカル適用前に記録を作り、適用とコメントの確認時に更新し、クローズ確認後に消す。記録が残った場合は一覧と次の開始・取り込み要求に進捗を表示し、GitHub への書き込みは自動で再試行しない。
- 接続時と再接続時には稼働中のターンと作業役を送り、引き取り後に中断した作業は元のジョブ ID で終了を記録する。待機画面には対象 ID・経過時間・承認待ちかどうかを表示し、5 分を過ぎたら経過分数も表示する。
- 方針からの新規委譲と自動の計画確認は、Preparing の開始から保留する。計画確認は同じスレッドでまとめ、更新状態に保留件数を表示する。失敗・中止時は稼働版で保留を解除し、入れ替え時は起動確認後に現在の手順を照合して再開する。前のサーバーが引き取り後に停止した方針の委譲には一度分の再試行を記録し、その試行も中断した場合は確認待ちにする。`[delegate].hold_planner_during_update = false` を指定したワークスペースでは、従来どおり Draining から保留する。
- シグナルによる停止では、実行中の受付・方針役・作業役に、いまの仕事を安全な区切りまで片付け、成果・残件・再開方法を保存して終了するよう通知する。Claude の受付にはタイムラインに通知し、実行中のターンの結果をチェックポイントに保存する。stream-json に追加の入力を送ると別のターンが始まり得るため、通知にはタイムラインを使う。通知は更新の待機 ID と対象の仕事に結びつける。新たな仕事の開始は閉じたまま、ファイル保存、権限内のコミット、報告、既に出た承認への応答、停止は受け付ける。実行中のテストやビルドなども終了・結果保存か明示的な停止まで追跡する。
- 既存の計画 `threads/<id>/plan.md`、会話・作業ログ、セッション記録を使う。仕事ごとにワークスペース・スレッド・ジョブの ID、完了／中断と理由、成果物のパス、必要に応じて worktree・ブランチ・コミット、残件・待っている判断・次に行う手順を残す。一時領域の成果は掃除の前に永続領域に移す。完了した仕事には完了結果を残し、続きがある仕事には再開地点と再開可否を残す。保存に失敗した仕事には待機画面で理由を示し、保存の再試行か更新の中止を選べるようにする。
- 47 番の待機画面は `SelfUpdateStatus` を使い、Draining の経過秒、対象ワークスペース・スレッド、退勤中・保存待ち・承認待ちなどの理由を表示する。保留済みと入れ替えを止めている仕事を表示で区別する。55 番のチャット欄は同じ工程を読み、実行中の表示との重複を避ける。通常の更新は `[self_update].wait_stall_seconds`（既定 300 秒）を期限として終了と保存を確認する。現在の待機 ID に対する明示的な強制操作を受けると `Forcing` と `interrupt_for_swap` に進む。保留入力を保存し、中断要求に応答しない Claude は猶予後に終了する。直接ループバックの HTTP 操作はクライアント接続が切れていても使える。 [設定と操作](../../docs/update.md#サーバーの入れ替え待ち)中断地点が未確認の仕事は、その理由と残った成果を記録して確認待ちにする。停止・保存の確認が取れない間は入れ替えを進めない。
- 中止は排他を取って入れ替えを確定する前に受け付ける。配信されていない退勤指示を取り消し、指示済みで稼働中の役には中止を通知する。退勤済みの仕事と保留は同じ稼働版で再開条件に従う。引き渡し前のエラーや監督への引き渡しを伴わない再起動でも、保留記録を読み、同じ経路で受付を開き直す。
- 入れ替え・復帰に使う両方の版で、保留レコードの読み戻しまたは回収を可能にする。自動復元ができない旧版には、その版が読める既存の停止・休止状態を使って該当作業の自動開始を止める。既存のスレッドから保留内容と回収手順を辿れるようにし、対応版での再評価か利用者の判断を待つ。切り替え前にこの保護を確認する。
- 保留の引き取りと完了を安定した ID で記録する。起動確認中のプロセスには引き取りを許さず、使う版が確定してから一つのプロセスに許す。実行が始まったか、外部操作が完了したかを確定できない記録は確認待ちにする。 採用した引き継ぎ作業と研究 Issue の作業は呼び出し元が結果を検証・反映する。再起動でその処理が失われたときは、保存した依頼・作業場所・成果から確認して再開する。

### 受け入れ条件

| 操作・条件 | 確認する結果 |
| --- | --- |
| ビルド・テスト中と試運転の昇格待ちに、新規委譲、目標の継続、入力、監視イベントを起こす。候補準備を失敗させる。 | 自己更新の準備中は方針役の自動委譲と計画確認を保留し、失敗時に再開する。利用者の依頼による作業、試運転中やクライアント単独の更新中の作業は継続する。 |
| 複数ワークスペースで候補準備の完了とターン開始、委譲・再帰委譲、スロットの解放を競合させる。 | 境界前に開始できたものはすべて待機理由に載る。境界後の開始はゼロ。受理済みの保留と受理前の応答を判別できる。 |
| 使用量休止の解除、受付済み入力、作業報告、自動再計画、監視通知を待機中に重ねる。 | 状態・本文・添付・成果・イベントが残り、保存済みの保留は Ready を妨げない。Running 復帰後は各条件を満たす項目だけが順序どおり一度配送される。監視はクライアント未接続でも再開する。 |
| 実行中の仕事を退勤させ、保存エラーや待機期限超過を起こす。 | 終了に必要な保存・承認・報告・停止が通る。保存エラーは対象と理由が見え、解決まで Ready に進まない。進捗が途絶えると自動で強制に切り替わり、停止と保存を確認できない場合は更新が失敗して受付が再開する。 |
| 47 番の画面から中止、続いて別の更新で強制入れ替えを試す。 | 待機 ID が異なる古い操作は無効。中止では同じ版で保留を再評価する。強制では保留入力が残り、再開地点の未確認な仕事は確認待ちになる。停止に失敗した仕事があれば、理由が残り入れ替えは進まない。 |
| 正常な入れ替え、起動確認の失敗と旧版復帰、手動の旧版への入れ替え、引き取り直前・直後の再起動を試す。 | 起動確認と切り替え結果の確定まで新規開始はゼロ。確定後は選ばれた一つの稼働版が成果・再開地点・保留を読み戻す。自動復元に非対応の旧版でも回収できる。完了済みの仕事の再開、依頼の消失、二重開始がなく、復帰失敗時も回収先が残る。 |

## 改名前の監督での入れ替え

新版は旧監督が渡す起動確認用の環境変数も受け付ける。その間は旧状態ディレクトリを使い、旧監督が `current` と `previous` を切り替えられるようにする。

旧監督を使う場合は、事前に新版をビルドする。旧版と同じ環境（アドレス指定、作業ディレクトリ、XDG 設定）で実施する。`old_pid` は停止する旧サーバーの PID、`old_binary` はその実行ファイル、`new_binary` は今回ビルドした絶対パス、`project` は起動時のプロジェクト引数とする。サービスからの自動再起動は止めておく。

```sh
builds=${XDG_STATE_HOME:-$HOME/.local/state}/labo-gui/server-builds
mkdir -p "$builds"
handoff=$(mktemp -d "$builds/rename.XXXXXXXX")
cp -p -- "$old_binary" "$handoff/labo-server"
cp -p -- "$new_binary" "$handoff/secretaire"
kill -TERM "$old_pid"
while kill -0 "$old_pid" 2>/dev/null; do sleep 1; done
export LABO_SELF_UPDATE_SOURCE="$HOME/fuzukue" # 実際のチェックアウトを指定
(
  flock -x 9
  exec "$handoff/labo-server" self-swap "$old_pid" "$builds" \
    "$handoff/labo-server" "$handoff/secretaire" "$project" <&9
) 9>>"$builds/lock"
readlink -f "$builds/current"
```

起動確認に通れば `current` は新版、`previous` は旧版を指す。切り替えを確認後、新版を停止する。起動確認用の環境変数が設定されていない通常の環境で、旧状態ルートの `server-builds/current` を一度起動する。新版が状態ディレクトリを移し、旧監督が作った絶対リンクを修正する。次の起動からは新状態ルートの `server-builds/current` を使う。
