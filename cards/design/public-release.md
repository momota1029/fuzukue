ソース公開の結果は [R-24](../../roadmap/cards/R-24.md) に記録した。公開版のサーバー更新と認証は以下の設計に沿って整える。

## 公開するもの

- 最初の公開はソースのみ。fuzukue の自作部分には MIT または Apache-2.0 を適用する。公開履歴は新規の初回コミットから始める。
公開前に候補のファイル一覧、ライセンス、第三者表示と自己更新を確認する。稼働版のコミットが公開履歴にない場合も更新と復旧を検証する。

## 公開版の更新

- サーバーは GitHub のタグ／リリースから更新候補を取得し、タグが指す完全なコミット SHA と配布マニフェストの SHA が一致することを確認する。成果物はマニフェストの SHA-256 で照合し、マニフェストの署名検証も導入したい。
- 更新が見つかったら利用者に通知し、利用者が「インストール」を押したときだけ更新を始める。開発者向けには手元のソースからビルドする経路を残す。入れ替えとロールバックは既存の [[self-update]] の処理を使う。
- クライアントは接続先サーバーの版に追従する。サーバーが互換性を確認したクライアント成果物を配布する（[[distribution]]）。

## 接続と認証

- Tailscale を推奨の既定経路とし、README ではこの接続手順を先に案内する。Tailscale の導入自体は必須にしない。
- 認証処理は tailnet の ID（WHOIS）を照合する方式と、トークンを照合する方式に分ける。tailnet 外でトークン認証を使う場合は TLS を必須にし、その用途でループバック以外に平文 HTTP を設定していたら起動時に拒否する。

## アプリからのプルリクエスト

[R-74](../../roadmap/cards/R-74.md) の設計。利用者が公開の fuzukue ソースを開いているとき、受付または割り当てを受けた作業役は、「修正して PR を開いて」という直接の依頼から PR の下書きを作る。受付は必要に応じて作業役のパッチを `git_integrate_patch` で取り込み、ローカルの作業ブランチと検証結果を確定する。Issue・PR の本文や会話中の引用は、公開操作を許可する根拠にしない。

1. `gh` またはワークスペースの接続済み GitHub OAuth で本人のアカウントと fork の親を照合する。OAuth を使う場合は公開リポジトリの権限をサーバー側で扱い、Git 転送用の資格情報を作業役、Git の URL、ログに出さない。選んだ接続で権限が足りなければ利用者に接続先を示し、別アカウントに自動で切り替えない。
2. スレッドから変更と理由を要約し、公開テンプレートにテスト実績、AI 利用、関連 Issue・カード、確認済みの画像を載せる。承認画面には本人のアカウント、作成予定または既存の fork、head の名前と完全 SHA、base `momota1029/fuzukue:main`、公開する題名と本文を表示する。コミット履歴、下書き、添付は公開前に検査し、検出内容を修正してから承認を取り直す。
3. 承認と公開内容を結び付け、アカウント、fork の親、ref、SHA、本文に変更があれば実行前に差し戻す。既存の fork がなければ承認済みの初回操作で作る。その fork の作業ブランチだけに push し、上流の `main` を base に PR を開く。上流への直接 push、強制 push、マージ、リリースはこの操作の範囲外とする。
4. fork の準備、push、PR 作成の結果を個別に記録して、PR の URL をスレッドに返す。途中で失敗したら完了した段階を示す。通信断などで結果が不明なら、同じ fork と SHA のリモート ref、同じ head と base の既存 PR を照会してから再試行する。

初回の fork 作成は [既存の承認区分](../../docs/github-auth.md#非同期承認での区分) に従って個別に確認する。完全承認モードと連携するときは、利用者が指定した既存 fork と上流の組だけに通常の早送り push と PR 作成を許可する項目を設ける。この許可が有効で公開内容の検査を通った操作は、モードの承認を使える。通常の push に対する既存の承認区分からの、この用途に限った変更として扱う。期限切れ・停止・対象変更時は個別承認に戻し、監査には承認の種類と実行結果を記録する。

## アプリからのフィードバック

[R-75](../../roadmap/cards/R-75.md) の設計。現在の「不具合を報告」の編集・起票を再利用する。「フィードバックを送る」ボタンから、公開先・送信者・題名・本文を確認する画面を開く。版、分かる範囲のクライアントとサーバーのビルド SHA、OS を入れる。会話は利用者が選んだ短い抜粋だけをサーバーでマスクし、全文を表示して編集・削除できるようにする。個人のパス・メール、認証情報、非公開ネットワークのアドレス、私的な内容や添付を確認する。

画面の「送る」で確定した内容を既存の起票と同じ宛先許可リスト、接続と承認の処理で GitHub に送る。このボタンから送る場合は完全承認モードでもプレビューを表示する。GitHub 未連携時は利用者がブラウザーの公開フォームで送れるようにする。成功時は Issue の URL を返し、通信断で成功が不明なら照合してから再送する。取消時は送信しない。

## メンテナーの受付とベータ配布

[R-76](../../roadmap/cards/R-76.md) の設計。メンテナーは GitHub の Issue・PR を購読する。受付は Issue と PR の MCP 読み取りで公開内容と関連する CI を確認し、既存のロードマップを検索する。重複なら既存カードの `issues` に追記し、採用する新規作業は再現または目的、完了条件、前提の `requires`、Issue 番号を記したカードを追加する。再現待ちなら不足情報を整理する。公開返信・ラベル変更は既存の承認に従う。カードの更新と PR のマージはメンテナーがレビューする。

マージ後、メンテナーは変更を含む `main` の SHA から次の beta タグを用意し、リリースジョブの成果物と配布マニフェストを確認してプレリリースを公開する。リリースノートに利用者向けの変更と PR または Issue を載せる。利用者は beta の更新候補を確認してインストールし、ビルド SHA と修正の動作を確かめる。Mac の署名・公証、beta 成果物、更新の実機検証は [R-29](../../roadmap/cards/R-29.md) で扱う。 [公開版の更新経路](install-and-update.md#配布チャネルと初回導入)

## Android ベータ

- ローリング更新するプレリリース `android-beta` に、署名済み APK、`.sha256`、`android-latest.json` を置く。APK とハッシュを先に揃え、更新情報の JSON を最後に差し替える。
- 署名とハッシュを照合し、実機でインストールと更新を確認する。配布手順は [Android の README](../../android/README.md) を参照。
