## 決定（2026-11-25、ユーザー）

スレッドはワークスペースごとに持つ。研究中に fuzukue の不具合や改善案に気づいたら、そのスレッドから fuzukue のワークスペースへ依頼を送れる。境界を越えるのは、利用者が送り先と中身を確認した依頼だけ。研究の会話、カード、資料、作業状態は元のワークスペースに置く。

依頼はまず同じサーバー内で届ける。友人からの要望など、利用者が公開できると判断したものは GitHub に出せる。送信前には宛先、本文、添付一覧を必ず見せる。完全承認モードでも、利用者が表示された内容を送ると決めてから配送する。

## 送る、受け取る、返す

- 元のスレッドで「いまの不具合を fuzukue に送って」「この Python を見本にして組み込みを頼んで」と話す。受付は何が起きたか、どう動いてほしいか、必要なら研究内容から切り離した最小の再現手順を下書きにする。研究の内容は入れず、固有の入力は合成した見本に置き換える。利用者は同じ会話で宛先と題名・本文を直し、選んだファイルの一覧と中身を確かめて「送る」か「やめる」を選べる。確認後に宛先・本文・添付が変われば、更新した内容をもう一度見せる。
- 宛先の受信箱に一件として届く。受信側は依頼本文も添付も外部資料として読み、自分の規則で作業内容、権限、必要な確認を決める。送信側の承認や作業状態は引き継がない。初期案では受信側ワークスペースごとに「受信箱に積む」（既定）と「受付が着手する」を選ぶ。自動で着手する設定は、受信側で要約・計画・作業の開始を許す。依頼の文面は指示や承認にならず、添付の実行・有効化を起こさない。
- 受け取り、質問、完了、結果は短く元のスレッドに返す。受付済みなど定型の状態は自動で返せる。質問や結果の本文は返す側で送る内容を確認してから届ける。質問への回答も同じ依頼への追記として確認して送る。送り元の会話や受信側の作業ログを開く権限は渡さない。
- 最初の入口は会話、確認は同じスレッドの一枚、到着は既存の受信箱、返事は元の会話の一行を基本にする。添付の詳細はその場で開く。

## 動く見本を添えた依頼

動く Python やスキルに書いた規則がすでにあり、製品に組み込むと便利になる場合も、一件の依頼として扱う。見本は Issue の文章だけでは伝わりにくい振る舞いを示す。取り込み先と実装方法は、受信側が見本を読んで決める。

受付は会話から次を一枚にまとめる。足りない項目は下書きで尋ねる。

- 何をするものか、どんな場面で使い、今はどう呼び出しているか。手順、実行環境、依存物、必要な設定を、公開できる範囲またはローカルで共有できる範囲で書く。
- 動く試作の Python、または規則を記した `SKILL.md` と必要な付属ファイル。利用者が共有対象をファイル単位で選ぶ。
- 入力例と対応する期待出力。順序、空入力、異常時など意味のある差は例に含める。スキルの規則なら、入力例に対して「何をするか」「何を避けるか」を説明できる。たとえば「重複したメモ名を先頭出現順で一つずつ残す。入力は A・B・A、期待出力は A・B」とし、研究の実データは使わない。
- 作者名、元の版やコミット、ライセンスまたは再利用許可の範囲。第三者のコード、資料、依存物も条件を確認する。許可が不明なら受信側で問い合わせ、許可が確認できるまで複製・改変・公開を伴う取り込みを保留する。

受信側は見本を読んで、次のいずれかを選ぶ。

1. **そのまま採用する。** 規則にはスキル、許可されたコマンドにはレシピ、製品の画面やイベントなどに接続する機能には拡張を使う。現行の読み込み・権限の仕組みを通す。導入前に差分、依存物、権限と作者表示を確認し、受信先で試して入出力を確かめる。
2. **製品に組み込む。** Python や規則を振る舞いの参照にし、該当する処理を Rust で実装する。製品の通常の入口から、受け取った入出力例を承認済みの受け入れテストとして使う。必要なら境界条件を足し、見本と意図的に異なる動作は理由とともに返す。参照した版、作者、再利用条件を作業記録に残し、取り込んだファイルやテストでは必要な表示と許諾文を保つ。

返事には採用した方法、使い方、使える版または取り込み先、移行時の注意を添える。元の試作を手元で止められるかは、受信側で使える版と残る手作業を示し、送り手が判断する。

## 添付と配送

- 添付は明示的に選ばれた通常ファイルの固定コピーを送る。フォルダーを選べる場合も、展開した一覧から対象を確定する。プレビューに本文、ファイル名、種類、サイズ、テキストの内容、共有する出どころを出す。シンボリックリンク、範囲外のパス、アーカイブを拒否し、依存ファイル・外部 URL を再帰的に取り込まない。確認したコピーの SHA-256 を保存し、送信時と受信時に照合する。ハッシュは内容の同一性を示し、作者や許可の確認は別途行う。
- 最初の添付対応は UTF-8 の Python、Markdown、プレーンテキスト、JSON、CSV、TOML とライセンス文書に絞る。上限の案は 16 ファイル、各 1 MiB、合計 8 MiB。件数・サイズ・形式をサーバーでも検査し、超えるときは説明を出して選び直せる。Wasm パッケージを使う場合も、まずソースとマニフェストをレビューし、採用先でコンポーネントを用意する。バイナリの添付は検査とプレビューを設計してから加える。
- 本文、ファイル名、内容、リンク、公開候補のメタデータを確認する。認証情報、実データ、未公開研究の本文・ログ、非公開 URL、個人情報があれば表示して除外・置換を求める。自動検査は漏れを防ぐ補助とし、利用者は実際に出る中身を確かめる。受信箱の資料はプレーンな表示で読み、到着時にコードを実行したり、スキルや拡張として読み込んだりしない。採用時も同名の設定やファイルの上書きは差分で確かめる。
- サーバー側に依頼 ID、宛先、送信元のワークスペースとスレッドへの返信経路、確認済みの本文、添付と来歴、受け取り・返事の状態を保持する。配送用の ID と返信経路はサーバー内に留める。宛先から元のワークスペースやスレッドを読み出す手段にはしない。保管先はリポジトリ外のサーバー状態とし、プレビュー・配送はワークスペース権限で絞る。同じ依頼 ID の再送では受信項目を増やさず、再起動しても受信と返事を取り違えない。添付がそろってから受信項目を表示する。

## 現行の仕組みを使うところ

| 現行 | 依頼での使い方 |
| --- | --- |
| 引き継ぎの Markdown、受け入れ条件、受信後の作業スレッド、重複防止 | 短い依頼文と着手時の流れに使う。引き継ぎノートに含める元の記録パス、作業者 ID、worktree、継続用の文脈は渡さない。 [引き継ぎ](handoff.md) |
| 研究 Issue の入口カード・作業場、作業役の振り分けと検証 | 宛先で作業にするとき、そのワークスペースの既存の仕事の始め方を使う。研究 Issue を作る場合のカード文脈と worktree は宛先側の仕事のために使う。 [研究の作業場](research-workshop.md) |
| Issue 受付の外部資料扱い、短い受信カード、状態と応対方針、Issue・PR とスレッドの紐づけ | ローカルでも同じ受付の考え方を使う。公開時は既存の許可先、起票の承認、Issue URL と更新の紐づけを使う。 [Issue の受付](../../docs/issue-intake.md)、[紐づけ](issue-threads.md) |
| 受信箱の添付選択・転送・表示 | 選択と表示を流用する。現行の添付アップロードはプロジェクトの `inbox/YYYY-MM-DD/` へ置く。依頼では表示の入口を共有し、依頼と添付は上記のサーバー状態に置く。 [添付の保存](../../crates/secretaire/src/inbox.rs#L90)、[受信箱の表示](../../crates/fuzukue/src/sidebar.rs#L614) |
| メモの一行入力と出どころ | 会話で下書きを頼む手軽さと来歴の記録を参考にする。元の発言を転記する `from:` と Git に入るメモは、依頼の配送に使わない。 [メモ](memos.md) |

新しく必要なのは、サーバー内の配送と返信、確認した内容を固定する送信、受信側の着手設定、見本の添付・来歴・採用結果を依頼に持たせる仕組み。

### 採用先の読み込み

- **スキル**は `skills/<name>/SKILL.md` と付属ファイルの単位で、受信側の手元の規則か `[[rules]]` のパックに置く。現行は選ばれたスキルを Claude のプラグイン（非対応時は追加ディレクトリ）または Codex の `skills/extraRoots/set` で渡す。引き継ぎの明示的な有効化も参考にする。 [規則パック](rule-packs.md#実装)、[引き継ぎの実装](handoff.md#実装)
- **Python スクリプト**は、必要なら受信先のレビュー済みファイルを呼ぶレシピにする。コマンドは作業ツリーの外に置くサーバー設定の許可リストで利用者が設定し、起動時に読み込まれる。ワークスペースの設定や受信内容からレシピは登録できない。現行の隔離、引数の検証、時間・メモリ制限を使う。 [作業役のレシピ](../../docs/recipes.md)
- **拡張**は `extension.toml` と任意の WIT 準拠の Wasm コンポーネントを持つパッケージを、プロジェクトか利用者の `[[extensions]]` に登録する。現行のロック、Wasm の SHA-256、版ごとの権限確認を使う。宣言に含まれる指示もパッケージ全体のレビュー対象。現行の拡張ローダーが実行するのは Wasm コンポーネントで、受け取った `.py` はスクリプトのまま拡張に登録できない。 [拡張機能](../../docs/extensions.md)、[Wasm ランタイム](../../crates/secretaire/src/extensions/runtime.rs)

## 公開できる依頼を GitHub に出す

公開用の下書きに、期待する動作、使い方、見本と入出力例、作者表示と許可をまとめる。投稿は既存の起票先の許可・確認を通す。Issue、Gist、fork の各宛先へ出る内容を送信前に見せる。非公開の依頼を丸ごと転載する操作は設けず、公開用に選び直した本文とファイルだけを使う。見本に許可がなければ公開版の合成例を用意するか、ローカルの依頼のままにする。公開 Issue と成果の PR は紐づけ、採用した方法と使える版は承認したコメントで返せる。元のスレッドには URL と短い結果を記録する。

公式資料を確認（2026-11-25）。Issue 作成・更新の REST API の本文は文字列で、一般ファイルをアップロードする項目はない。ブラウザーには対応形式の添付操作があり、GitHub CLI の `gh issue create --attach` は画像・動画を扱う。CLI では一部の添付に失敗しても Issue が作られることがある。別の Issue Artifacts REST API は起票後に `name` と文字列の `body` で Markdown やリンクなどを登録できる公開プレビューで、任意のファイルをそのままアップロードする仕様は確認できない。この設計では公式文書上の対応を確認し、実際のアップロード試験は行っていない。 [Issue の REST API](https://docs.github.com/en/rest/issues/issues#create-an-issue)、[添付できるファイル](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)、[GitHub CLI](https://cli.github.com/manual/gh_issue_create)、[Issue artifacts の使い方](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/using-artifacts-with-issues)、[Issue Artifacts の REST API](https://docs.github.com/en/rest/issues/artifacts#create-an-issue-artifact)

| 公開方法 | 使いどころ |
| --- | --- |
| Issue 本文のコードブロック | 小さな Python または規則と少数の入出力例を一緒に読む。最初の公開経路に使う。ファイル名と適用範囲を添える。 [コードブロック](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-and-highlighting-code-blocks) |
| Gist の固定版を Issue にリンク | 複数の小さなテキストファイルをファイル名付きで共有する。版、作者、ライセンスを記し、Issue には何を取り込んでほしいかを書く。secret Gist も URL を知る第三者が閲覧できるので、公開可能なものに限る。 [Gist の公開範囲](https://docs.github.com/en/get-started/writing-on-github/editing-and-sharing-content-with-gists/creating-gists)、[Gist の REST API](https://docs.github.com/en/rest/gists/gists#create-a-gist) |
| Issue と fork からの PR | 決まった採用先へ実装とテストを提案する場合は PR にする。見本だけを共有するときは公開可能なファイルだけを置いたコミットを Issue から参照し、製品への差分ができた時点で PR を紐づける。公開前にコミット、差分、履歴も確認する。 [fork からの PR](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/creating-a-pull-request-from-a-fork) |

## 実装の順序と完了条件

1. [R-91](../../roadmap/cards/R-91.md) は本文だけで往復できる最小の経路。研究中の操作を合成した例で、別ワークスペースの受信箱に一件だけ届き、受信側の判断で着手し、質問と完了が元のスレッドに戻ることを確かめる。
2. [R-92](../../roadmap/cards/R-92.md) は動く見本と受信側の自動着手設定。Python とスキルの例で、承認済みの添付だけが届き、受信だけでは実行されず、現行の経路での採用か入出力を使った Rust 実装の結果を返せることを確かめる。
3. [R-93](../../roadmap/cards/R-93.md) は公開用の Issue。初回は本文と短いコード例を既存の起票で届け、公開本文と対象ファイルだけが送られ、Issue と結果が元のスレッドで追えることを確かめる。Gist と fork からの PR は用途に応じて利用者が選ぶ。新しい自動アップロードは前提としない。
