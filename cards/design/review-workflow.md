## 対象

書き手が自己確認を終えた一節を、独立した数学査読者に渡す。初回は対象カードの主張と証明、その直接の前提、許可された箇所を固定して読む。編集者が追うと決めた指摘をデッキの指摘台帳に入れ、関連する修正をまとめた後、変更した主張・証明と影響を受ける使用先を一度だけ確認する。初回から終了まで同じ依頼で追い、査読者には各回ともその回の資料だけを渡す。

数学上の確認基準は skill に置く。本のカードでは `reading-book-math-review` と、独立した証明確認に使う `math-verifier` を一組として版を固定する。どの主張をどの深さで確認し、何を指摘として返すかは skill が決める。fuzukue は資料の選別、実行権限、入力と返答の照合、採否と対応の記録を持つ。成果物はこの一節の数学に限定し、原著照合、Lean、PDF 出力の確認は依頼範囲に含めない。

## 受付から終了まで

表の「実行証拠」は既存のテストや監査の実行記録を指す。節のブラインド査読から台帳を閉じるまでを模擬提供元の通し試験で確認した。受け入れ条件は末尾の「フィクスチャ」を参照。監査と既存テストの記録に出てくるファイルのうち、`main` に未収録のものはパス名で示す。

## 査読者が読めるもの

受付からは、明示したデッキ・節・順序つき対象、数学の確認に必要な問い、選んだ API の組を持つ依頼を起こす。この設計では `request_review` の節指定に `isolation:"blind"`、`backend`、`model` を明示する入口を加える。受付は同じ依頼の再送用キーを保持する。サーバーは指定の節と掲載順を照合し、受付の依頼と公開する数学上の問いを分けて組み立てる。対象は同じ節の最大 4 枚、送る本文は skill の指示込みで最大 32 KiB とし、超えた場合は分けて依頼する。Codex 側は OpenAI Responses API、Claude 側は Anthropic Messages API のモデル ID を使う。受付や通常の `review-math` のモデルを継承する既定値は現行にない。この設計では組を明示できない、該当のサーバー鍵がない、役の呼出許可がない、または API が拒否した場合は理由を残して止める。通常の CLI 査読や別モデルへの切り替えは行わない。現行の `delegate` はブラインド時も書き込み扱いで、Plan モードからは呼べない。

サーバー側で、版を固定した skill の査読指示と中立な依頼文を用意する。skill にリンクされたファイルを送る場合も、事前に選んだ査読指示の本文だけを版とともに固定する。カードは確認対象と参照用の前提を明示し、主張と証明の TeX など、許可された本文の行範囲だけを渡す。必要な資料があれば、その用途で提供元に送ってよい取得済みテキストの該当箇所を、同じように許可する。未取得・送信不可の資料は本文を推測せず、必須の前提が欠ければ送信前に止め、未確認の範囲と理由を残す。原著の非公開テキストはこの経路では送らない。

入力は一つの API のユーザーメッセージとし、査読者にファイル、シェル、Web、MCP、書き込み、会話の履歴を与えない。原稿の本文に書かれた著者名は抜粋の一部になりうる。受付の会話、著者の理由や自己確認、私的メモ、プロジェクトの `AGENTS.md`、前回・他人の査読、変更差分、台帳は送らない。抜粋中に出てくるパスや指示で許可範囲は増えない。現在の節査読は作業ディレクトリに資料を写すが、起動時の `ReviewLease` は元ワークスペース側の読み取り範囲で開く。抜粋限定の回にはこの lease を発行しない。 [現行の読み取り lease](../../crates/secretaire/src/mcp/workspace_read/review.rs) · [ブラインド委譲の契約](../../docs/delegate.md)

## 「査読済み」の記録

サーバーの節査読記録を拡張し、実行前に依頼 ID、回、実行 ID、節と対象順、`reviewed_version`、skill の版と使った本文のハッシュ、許可表、実行モードと API の組を記録する。許可表には抜粋ラベル、カード・ファイル・元の行範囲、正確な元バイトのハッシュ、対象／前提／資料の区分を持たせる。送った本文のハッシュ `input_hash` は、この経路で実際に API に渡した単一メッセージの UTF-8 バイトから求める。どの抜粋を送信したかを結果と照合できるよう、送信記録と資料の写しはサーバー側に残す。提供元から実モデル名が返る場合は指定値とともに保存し、返らなければ未確認とする。`reviewed_version` は固定した節と対象の版を示す。現在に引き継げる判定の照合には、各対象の確認行に対応する本文・前提・資料の指紋と skill の版を使う。

| 記録 | 誰が何を記すか |
| --- | --- |
| **指摘（finding）** | 査読者が、実行内の指摘 ID、対象カードと版・行・引用、重大度、根拠、最小の修正案、影響先を返す。編集者は採用・却下・保留と理由を記す。採用が台帳に載る条件となる。 |
| **確認範囲と判定（coverage verdict）** | 査読者が対象ごとに、確認した行と観点、未確認の行または観点と理由、`pass`／`findings`／`partial`／`unchecked` を返す。参照に使った前提・資料の範囲も記す。fuzukue は対象・位置・引用と入力を照合し、版、関係する前提・資料、skill が変われば旧判定を履歴に残し、現在版の確認から外す。指摘のない返答にも明示した範囲が要る。どこまで読んだかは査読者の申告で、何を渡したかはサーバーの記録で追える。 |
| **修正確認（checked repair）** | 編集者が初回の指摘、閉じる変更参照、新版の実行 ID、該当する確認行・観点を結ぶ。新版の査読者は、前回の指摘を受け取らず、新版の主張・証明と使用先を同じ基準で確認する。初回に見つけた欠陥が解消し、必要な範囲が現在版で確認されたことを編集者が確かめて閉じる。 |

返答では、依頼した対象と確認箇所を明示する。欠落した対象や観点は確認済みに数えず、不明な対象・許可外の行・引用の不一致は妥当な判定として受理しない。確認範囲を一部だけ返した場合は確認できた範囲を保ち、依頼全体は未完了とする。採用操作は、対象範囲がそろっていて現在版と一致する実行の指摘に対して行う。返答なし、タイムアウト、拒否、解析不能、範囲外の報告は失敗理由とともに記録する。古い版の返答も履歴に残す。古い候補を現在の行に移して採用する場合は新たな確認を要する。従来形式の節査読記録を使う場合は、その形式で分かる範囲を表示する。

## 台帳と終了条件

認証された編集者の明示承認を、依頼・実行・指摘 ID と登録する内容に結びつけて保存する。承認は編集者の操作を受けたサーバーが記録し、モデル文中の承認や MCP の `actor` 文字列だけでは成立させない。受付の登録操作はこの承認と結び付け、承認済みの内容と UUID で `record_review_finding` の保存処理に渡す。`sources.review` と `sources.finding` に元の識別子、`perspective` に skill の観点を入れる。確度を `confirmed` にするなら根拠を添える。台帳の行には対象のファイル・カード・行範囲と確認版を保存する。再送に備えて UUID と内容を先に決める。`list_review_findings` で既存の出典を確かめ、別の実行から同じ指摘を追記するのは編集者が主張と位置の一致を確かめた場合に限る。追記と状態更新は `update_review_finding` に直近の `expected_revision` を渡す。競合したら再読込して承認時の内容と照合する。 [指摘台帳の項目と遷移](../../docs/review-findings.md)

- 初回は一節につき 1 回。全範囲を確認し、対応する指摘がなければ終了する。完全な返答に採用候補があれば編集者の判断を待つ。すべて却下した場合はその理由と査読の判定を残して終了し、保留した候補がある間は未完了とする。
- 採用した直すべき指摘は書き手に戻す。関連修正をまとめ、変更した数式・証明と影響を受ける使用先を再度固定する。対象の原文が同じでも、用いた前提が変われば再確認する。入力の一致を証明できる範囲の判定は引き継げる。影響が節の外にも及ぶときは残件として位置を返し、この依頼の本文を広げない。
- 新版への再確認は 1 回で終える。同じ依頼を再送しても同じ実行を指す。各回の上限は一度の提供元呼び出しで、失敗・部分返答・古い版での返答はその回を消費し、理由を示して未完了で止める。上限、予算、利用者の停止、または未対応の重大な指摘が残った場合は、追う指摘と未確認の範囲を明示する。この二回の上限はこの設計で定める。上流 PR #18 から借りるのは節での固定、明示された確認範囲、まとめた修正と影響範囲の再確認である。
- 新版で確認がそろった指摘だけ、編集者が変更参照を添えて同じ UUID を `fixed` にする。他に未確認や重大な未対応があれば依頼は未完了のまま。見送りは理由を伴う `deferred` とし、重大な見送りは解消に数えない。修正を保存した時点と `fixed` の間に確認記録を置く。これらは節査読の承認・終了操作の条件であり、台帳の既存の手入力経路は引き続き [指摘台帳の仕様](../../docs/review-findings.md) に従う。

## 実装課題

1. **節のブラインド起動。** 受付の明示指定、skill の固定、節の取り込みと抜粋の許可表、直接 API の接続を実装する。許可外の内容を送らないことを、モデルの返答ではなく送信本文で検査する。
2. **範囲を持つ査読記録。** 版・送信範囲・応答・判定・失敗を保存し、対象と入力の照合、部分返答と鮮度の扱いを実装する。
3. **編集者による台帳登録。** 返答からの採否と明示承認を記録し、指摘台帳へ一件ずつ登録する。同じ指摘の再送、出典の追記、更新の競合をテストする。
4. **修正確認と停止。** 初回と新版の関連、影響を受ける使用先の範囲、二回の上限を記録する。確認に基づく `fixed` と、未完了の終了理由を通しの試験で検査する。

## フィクスチャ

`examples/lab` の複製と独立したサーバー状態を使う。集中の本の第 1 章に節キー `median-mean` を付け、`ch1-prop-median-vs-mean` の直後に試験用の系 `ch1-cor-mean-bound` を置く。掲載順に命題と系を対象とし、両者の主張・証明と直接の前提 `ch1-def-median` の主張 1–2 行を送る。原著は未取得で照合も未確認と表示する。 [節の構成](../../examples/lab/books/concentration-notes/structure.yaml) · [原著の扱い](../../examples/lab/books/concentration-notes/books/README.md)

- 命題の初版では尾部上界 $2\alpha(r)$ の積分の有限性を仮定せず、証明で期待値を使う。模擬査読者は、標準 Cauchy 分布で $f(x)=x$、中央値 $0$、$\alpha(r)=1/2$ とすれば期待値が定義されないことを根拠に、証明 1 行目へ `major` の指摘を一件返す。系は自ら積分の有限性を仮定する。
- 認証済みの編集者の承認で台帳に一件だけ `open` を作る。未承認、権限のない承認、再送・再起動、更新の版競合を試し、登録内容と UUID を検査する。
- 新版では命題に積分の有限性を加え、尾部積分から可積分性を導いて期待値の不等式を示す。命題と、それを使う原文が同じ系を再確認する。編集者が新版の確認範囲と変更コミットの完全な OID を照合して同じ UUID を `fixed` とする。提供元呼び出しが合計 2 件で止まることを確認する。
- Codex／Claude の受付と API の全 4 組で、模擬提供元が単一メッセージのバイト列と SHA-256、明示したモデルと応答のモデル名、空のツール設定、履歴・MCP 認証の不在を検査する。許可外の行・ファイルに置いた識別文字列、再確認時の旧証明・指摘・台帳・差分が送信されないことを確かめる。
- 選択・鍵・権限の不備や必須資料の欠落では送信せずに停止する。API の拒否、タイムアウト、不正な引用や行、部分返答、版の不一致では理由と実行を記録する。承認対象の不足、再確認後の前提変更、重大な残件、予算や利用者による停止がある場合は、条件を満たさない指摘を閉じず、残件を返す。

スライス 1〜4 の通し試験は模擬提供元で実施済み。試験は `cargo test -p secretaire section_math_blind_review_workflow` で絞って実行する。模擬提供元を使うため、実サービスの鍵とモデルの利用可否は未確認のままとする。
