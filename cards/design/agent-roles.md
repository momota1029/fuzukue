## 役の分け方

- 受付はスレッドの文脈を持ち続ける。方針役は次に進む手順を決め、作業役は証明、Lean 化、調査、執筆、実装を担う。
- 利用者と話す相手は一人。各役、進捗要約、査読の地の文に同じ AGENTS.md の口調を適用し、モデルと実行の記録は詳細に出す。
- 受付の設定は固定し、方針と作業には `light`、`standard`、`heavy` を使う。テスト失敗、停滞、自信不足、検証による棄却では上限まで一段ずつ上げて続ける（[[tiers]]）。
- 受付が重い仕事だと判断したら、作業役に渡す。渡すときは、受付がスレッドの文脈から作業に要る分を書き出して添える（作業役は会話の全部を読まない）。
- 切り替えは利用者から見て切れ目がない。
  - 作業役の発言と短い進捗要約は、同じ会話の中にジョブごとに出る。要約用のモデルの使用量が高いときは要約を省く。
  - 入力は既定で受付に届く。利用者はジョブを選んで作業役に直接送れる。受付は `message_worker` で指示を転送できる。
  - 作業役は `ask_front_desk` で不足する文脈を尋ねる。受付のターン中なら空くまで待つ。受付は `answer_worker` で答え、必要なら先に利用者に訊く。質問は三分で時間切れになる。
  - 作業結果は受付のターンの合間に一件ずつ届く。受付は利用者に結論を一、二文で伝える。
- `delegate` はジョブ ID をすぐに返す。サーバー全体で四件まで同時に走り、それを超えるジョブは空きを待つ。停止はジョブごとに行う。

## サブエージェントの定義

- 各ルール層の `agents/*.md` で定義する。YAML の先頭部分に `name`、一行の `description`、`backend`、`model`、任意の `effort`、`tools`、`tier` を書く。Markdown の本文が作業役への指示になる。`tools` を空にすると、作業役に公開しているすべての MCP 道具を使える。
- 組み込みを先に読み、後のルール層の同名定義で上書きする。同じ層の `agents/` と `skills/` で名前が重なれば、`agents/` を使う。
- スキルは `SKILL.md` の名前と説明で一覧に加わる。選ばれた作業役が全文と付属ファイルを使う。スキルにも既定の接続設定がある。
- 受付は名前と説明で作業役を選ぶ。設定の「エージェント」で、名前ごとにバックエンド、モデル、思考レベルを替えられる。委譲時はスレッドの情報欄で選んだ設定、ワークスペースの共通設定、定義の既定値の順に使う。設定を外すと一段下の設定に戻る。
- 文体・数学・Lean の自動査読にも共通設定の `review-style`、`review-math`、`review-lean` が効く。進捗要約には「進捗要約のモデル」の設定を使う。研究 Issue の作業役は既存のモデル名指定に加えて、作業場の設定でバックエンドとモデル、思考レベルを指定できる。

## チャットのスラッシュコマンド

- サーバーのコマンド登録簿は名前、日英の説明、引数、対応バックエンドと処理を定める。入力欄と `/help` は同じ一覧を使う。
- `/compact` は Claude Code のセッション用コマンドか Codex のスレッド圧縮を使う。組み込みの圧縮を使えない場合や、将来の OpenRouter などの API バックエンドでは、受付の文脈を要約して新しいセッションに引き継ぐ。

## Git

- 開いているワークスペースの変更の状態、差分、履歴を MCP の道具とスレッドの情報欄で見られるようにする。
- コミットは相談役か作業役が道具で作れる。push は外に出る操作なので、利用者の承認を通す。

## グラフ探索の MCP（本の執筆にも）

- デッキのカード（論文、研究、本）と、そのあいだの関係（`requires`、`links`、`from:`、本文中の参照、構成 `structure.yaml`）を、索引にしたグラフとして持つ。ファイルが変わったら、その分だけ索引を直す。
- 道具で、全体の見取り図（デッキ・章ごとのまとまりと要約）、近くのカード（深さを指定）、2 つのカードを結ぶ道、語での検索、未解決の参照や孤立したカードを、一度の呼び出しで返す。
- LLM が全体を掴むために何十ものファイルを開かずに済むようにする。本（`kind = "book"`）の章立てや、章をまたぐ参照にも使う。

## 方針役（2026-11-20、ユーザー）

>「そういえば相談役と方針役も分けるべきですね．低いモデルが高いモデルを使う構図だけだと「次に何をすべきか」の思考が浅くなって同じところをぐるぐるしてしまうんですよね．」

- 役を三つにする。**受付**（軽い。利用者と話し、仕事を回す）、**方針役**（重い思考。目標に対して次に何をするかを決める）、**作業役**（重い実行。決まった仕事をする）。接続先は設定で上書きできる。
- 方針役は、スレッドごとに「方針」を持つ。目標と完了の条件、済んだこと、次の一手（何を、どの作業役に、なぜ）、試して駄目だった道とその理由。方針はスレッドのファイルに残し、画面の情報欄で見られる。
- 方針役を呼ぶ時:
  - 目標のある仕事を始めるとき（受付が「軽い会話ではない」と判断したとき）。
  - 作業役の仕事が終わるたび。結果を方針と照らして、次の一手を決め直す。
  - 同じところを回っている兆しがあるとき。同じ種類の仕事が続けて失敗した、同じ質問が繰り返された、何ターンも方針が進んでいない、など。駄目だった道を見て、別の道か、利用者に訊くことを選ぶ。
  - 利用者が「どうするのがいい？」と訊いたとき。
- 受付は方針に沿って作業役を呼ぶ。方針にない大きな仕事を始めるときは方針役に相談する。方針役は利用者と直接は話さず、受付を通す（利用者から見て一人の相手のまま）。
- 使用量に合わせて進める長い仕事は、方針役の方針の上に載せる。

### 実装（2026-11-20）

- 受付は複数の手順が必要な依頼で `plan` を呼び、利用者から方針を相談されたときは `replan` を呼ぶ。情報欄の「方針を見直す」でも再検討できる。
- サーバーは `threads/<id>/plan.md` に目標、完了条件、済んだこと、次の手順、見送った方法と理由を保存します。方針役に渡す会話の文脈は、直近の依頼と作業報告の抜粋です。作業後は受付が結果を受け取る前に方針を更新します。情報欄はその状態を随時表示し、会話には「方針を更新」の一行を表示します。
- 同じ作業役で失敗・中断が二件続いたとき、同じ質問が二度届いたとき、四件の仕事で完了した手順が増えないときに、別の方法か利用者への確認を選びます。質問は受付が自分の言葉で伝えます。
- 長期目標には全力・ふつう・節約のペースを設定できます。節約時は方針と作業の段階を一段下げる。使用量による減速、休止、再開の目安は情報欄と入力欄に表示されます。
- `consult` は、設計の分かれ道、要件の衝突、危険や後戻りの難しい判断、同じ問いに二度行き詰まったときに、受付が方針役へ一問だけ相談する道具。現在の方針と直近の会話を添え、短い答えと、選択が必要なら最大三案と推奨案を返す。
- 相談中は入力欄の上に状態を表示し、使用量は方針役に記録する。呼び出しは既定で受付の一ターンに一回。上限は `FUZUKUE_CONSULT_CALLS_PER_TURN`、回答のトークン数の目安は `FUZUKUE_CONSULT_MAX_OUTPUT_TOKENS` で調整できる。

## サブエージェントの管理

- 組み込み、プロジェクトの定義、ルールパックのスキルを設定の「エージェント」に表示する。定義の先頭に `enabled`、`callers`、`when` を置ける。省略時は有効で、受付と方針役が呼び出せる。設定でワークスペースごとに上書きできる。`when` は使う場面を示す一行で、受付の `list_agents` と方針役の入力に名前・説明とともに載る。選ばれた作業役にだけ定義の本文とスキルの付属ファイルを渡す。
- 受付からの直接の委譲と、方針にある手順の実行を区別する。方針の手順を進めるときは、`delegate` に `plan_step: true` と、保存済み手順の `agent`・`task` を渡す。無効な定義や呼び出し元に許可がない定義は一覧から外れ、委譲にも使えない。`callers` に書ける値は `front_desk`、`planner`、`worker`。作業役から別の作業役を呼ぶ経路は現在ない。
- サーバーのワークスペース状態ディレクトリに `agent-usage.jsonl` を追記する。開始日時、スレッド、呼び出し元、役名、バックエンド、モデル、思考レベル、所要時間、結果、取得できたトークン数、ジョブ ID を記録する。作業の本文から残すのは先頭行の80文字まで。委譲の所要時間には待機時間を含む。現在分と前回分を各8 MiB程度まで残し、古い分の最終使用日時は別に保存する。
- 設定の各行で回数、成功率、最終使用日時を確認できる。「履歴」では最近の100件を役名・スレッドで絞り、委譲の行から会話の該当箇所へ移動できる。受付と方針役の `agent_stats` は、保存している記録から7日間・30日間の回数、成功率、所要時間の中央値、取得できた総トークン数を集計し、未使用の役も返す。

- 実機確認や選択が必要な手順は、受付が `block_step` に利用者の言語で短い理由を渡す。独立した手順に着手し、必要に応じて `replan` で新しい作業を探す。
- 次の手順に着手しない状態が60秒続けば、サーバーが受付に一度だけ促し、それでも動かなければ方針役が独立した作業を一度だけ探す。利用者による確認だけが残る場合は、確認内容を記録して目標を完了する。
