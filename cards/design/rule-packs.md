ユーザー（2026-11-19）:「普通にgithubからskill/文体/注意をDL・更新できる仕組みをもっと柔軟に作るべきではないかという気がしています．ソフトではなくてね．lab-rulesみたいなrepoでもいいですが」

## 形
```toml
# fuzukue.toml
[[rules]]
source = "github:example-owner/lab-rules"   # git の URL か手元のパス
rev = "v3"                                # タグ・ブランチ・コミット
[[rules]]
source = "../my-local-rules"
```
- パック = ただのファイルの集まり: `reviewers/*.md`（査読の指示）、`style/*.toml`（文体の規則）、`policy/*.md`（エージェントへの方針・注意）、
  `skills/*/SKILL.md`（skill）、`lint/*.toml`（未定義語の除外語など）。
- 重ね方: ソフトの既定 → パック（書いた順）→ プロジェクトの手元のファイル。後のものが勝つ。
- 固定と更新: 使っている版を `fuzukue.lock` に記録。「規則を更新」（MCP ツール・画面）で新しい版を取り、差分を見せてから固定し直す。勝手には変わらない。
  取ったものは `$XDG_CACHE_HOME/fuzukue/rules/<source>@<commit>/`（既定のキャッシュ根は `~/.cache`） に置く。
- skill: Claude には会話ごとに `--plugin-dir` で読み込ませる。Codex は app-server の `skills/extraRoots/set`。
- labo-skills には手を付けない。作法の部分をパックとして切り出すかは、ユーザーが決める。

## 実装

- secretaire は `fuzukue.toml` の `[[rules]]` を記載順に解決する。`github:owner/repo` は HTTPS の Git URL に展開し、Git CLI の認証設定を使う。Git のタグ・ブランチ・コミットを取得し、`fuzukue.lock` の `[[rules]]` に `source`、`rev`、`commit` を保存する。ローカルパックのパスはプロジェクト相対または絶対で指定でき、`rev` は無視する。
- キャッシュの名前には安全な文字に変換した取得先、取得先のハッシュ、コミットを使う。固定済みの版はキャッシュから読む。キャッシュを失った場合は `update_rules` で明示的に取得し直す。Git パック内のシンボリックリンクは拒否する。
- `rules_status` は固定コミットと指定した `rev` の現在のコミットを比較する。`update_rules` は対象（`source` 省略時は全 Git パック）を取得し、追加・変更・削除したファイルを返して `fuzukue.lock` を更新する。比較元のキャッシュがない場合は変更ファイルが `null` になる。タグを別のリリースに変えるには `fuzukue.toml` の `rev` を指定し直す。
- 査読指示は `reviewers/<kind>.md` の最優先のファイルを使う。文体と用語の設定は各ルートの `style/*.toml` と `lint/*.toml` をファイル名順に適用し、指定されたキーを上書きする。その上にデッキの `[style]`、`[lint]` と `style.toml` を重ねる。デッキの文体設定の `extra_phrases` と `disable` は従来どおり追記する。単体の `fuzukue-cards` には `--rules DIR` を複数回指定できる。
- ワークスペースの `[style_lint]` は検査の適用範囲を指定する。`enabled` の既定は `true` で、`exclude` の glob は既定の除外に追加する。[設定と表示](../../docs/graph.md#文体の指摘)
- `policy/*.md` は同名のファイルのうち最優先のものを残し、レイヤー順とファイル名順に既定の `POLICY` の後へ加える。skill は同名ディレクトリのうち最優先のものを付属ファイルごと使う。
- Claude には選ばれた skill をセッション用のプラグインにまとめて `--plugin-dir` で渡す。このフラグがヘルプにない CLI には、サーバー状態ディレクトリ下のセッション用 `.claude/skills` を `--add-dir` で渡す。Codex には新規スレッドの起動前に app-server の `skills/extraRoots/set` で渡す。既存の会話に渡したシステムプロンプトは会話の起動時点の版を使う。

## 直して送り返す（2026-11-20、ユーザー）

>「参照するカスタムスキルをどうするか考えたいのよね。スキル一つ一つをsubmoduleとして改変しながらプルリクを送るとやりやすくはありそう。他にフォークせずにプルリクを送る方法があるならそれはそれでいいけど」

決定（2026-11-20、ユーザー）:「いいね！　みんなでスキルを育てるのがよい。」

- submodule は使わない。今のパックの仕組み（`fuzukue.toml` の `[[rules]]`、`fuzukue.lock`、キャッシュ）の上に、「直している版」を足す。
- スキル（パックの中の一つのディレクトリ）を直すと、fuzukue がそのパックの手元の複製に、スキルごとのブランチ（例: `fuzukue/paper-writing-2026-11-20`）を切った作業ツリーを作り、そのワークスペースでは固定した版の代わりにこの作業ツリーを使う（画面に「直している版」と出す）。
- 「pull request を送る」で、そのブランチを送り、`gh pr create` で pull request を作る。
  - 親リポジトリに書ける場合（labo-skills は利用者が持ち主）は、親に直接ブランチを送る。fork は要らない。
  - 書けないパックでは、`gh` が自動で fork を作って送る（利用者が fork を手で用意する必要はない）。
  - 送るのは外への操作なので、毎回利用者の承認を通す。
- 取り込まれたら、固定を新しい版に移し、作業ツリーとブランチを片付ける。断られたら手元の版に戻す。
- 一つのスキルに一つのブランチと一つの pull request にして、fork 側の衝突を小さくする。

## 考えること（2026-11-20、ユーザー:「使わないスキルを置いておくかとか、拡張機能扱いにするかとか色々考えは山積よね」）

- 使わないスキル: 消さずに置いておき、無効にできるようにする（[[agent-roles]] のスキル管理の「有効・無効」）。呼ばれた記録から「30 日使われていない」を画面に出し、無効にするかを利用者が決める。受付に渡す一覧には有効なものだけが載るので、置いておくだけなら文脈は食わない。
- 拡張機能として扱うか: パックを「入れる・外す・更新する」単位にすると拡張機能に近い。案: 知っているパックの一覧（名前、説明、出どころ、入っている skill の数）を画面に出し、「入れる」で `fuzukue.toml` の `[[rules]]` に足す。パックの中の skill は一つずつ有効・無効にできる。
- まだ決めないこと: パックの一覧をどこに置くか（labo-skills の README か、別の小さな索引のリポジトリか）、他人のパックを入れるときの確かめ方（中身を読んでから入れる、版を固定する）。

## 自分のスキル集と、出どころの記録（2026-11-20、ユーザー）

>「あるリポジトリのどのファイル、というのまで書いておいてプルリクは都度なんかやるのがいいかもね。私のスキル、みたいな感じでまとめてリポジトリに置いときたいし。」

上の「パックの手元の複製にブランチを切る」形を改め、次にする。決定（2026-11-20、ユーザー）:「それにしましょう」

- 利用者は自分のスキル集のリポジトリ（例: `example-owner/my-skills`）を一つ持ち、使うスキルをそこにまとめて置く。fuzukue はこのリポジトリを規則パックとして読む。
- 各スキルに出どころを記録する。どのリポジトリの、どのパス（ファイルかディレクトリ）を、どの版から取ったか。

```toml
# my-skills/skills.toml
[[skill]]
name = "paper-writing"
path = "skills/paper-writing"
upstream = { repo = "github:example-owner/labo-skills", path = "skills/paper-writing", rev = "e51eba3" }

[[skill]]
name = "stat-repro"            # 自分で書いたもの。upstream なし
path = "skills/stat-repro"
```

- 直すのは自分のスキル集の中だけ。いつでも自由に直してコミットしてよい。
- **上流の変更を取り込む**: 出どころの記録した版から新しい版までの差分を、手元のスキルに三方向マージで当てる。ぶつかったら差分を見て選ぶ。取り込んだら記録の版を進める。
- **上流に送る（都度）**: 送りたいときだけ、記録した版からの手元の差分を、上流の新しいブランチに当てて pull request にする（持ち主なら上流に直接、そうでなければ `gh` が fork を作る）。外への操作なので毎回承認。取り込まれたら記録の版を進める。
- スキルを取ってくるとき（「このスキルを使いたい」）は、上流から自分のスキル集にコピーし、出どころを記録する。

ユーザー（2026-11-20）:「ただ、基本的なスキルはRustでかなりハーネスが組まれてほぼ組み込みになると思うのよね」
- 基本の仕事（論文の組み立て、カードの検査、査読、証明・Lean、本の取り込み、テスト、Git など）は、Rust のハーネスと組み込みのサブエージェント（`agents/*.md`）として fuzukue に入る。スキルの中身のうち、手順や検査は道具に、作法はサブエージェントのプロンプトに移る。
- 自分のスキル集は、組み込みに無いもの（分野ごとの作法、個人の書き方、試し中の手順）と、組み込みの振る舞いを上書きしたいものを置く場所になる。組み込みのサブエージェントも、同じ名前で上書きできる（後の層が勝つ）。

ユーザー（2026-11-20）:「あとハーネスの使い方やハーネスのなかで使うスキルなんかは育てることになるね」
- 道具（Rust）は固く、使い方は育てる、と分ける。育てるもの: 道具の使い方の手引き（どの道具をどの順で使うか、よくある失敗）、組み込みのサブエージェントのプロンプト、その中で使うスキル。
- 置き場所は自分のスキル集と同じ形にする。組み込み（`agents/*.md` や使い方の手引き）を上書きしたものは、出どころを fuzukue のリポジトリとして記録し、良くなったら fuzukue に pull request で返す（スキルと同じ「都度送る」）。
- 育てるきっかけを残す: スキル管理の呼び出しの記録（失敗の多いもの）、利用者が作業役の結果を直したこと（11 番の「人の編集」）、方針役が「駄目だった道」に書いたこと。これらを材料に、プロンプトや手引きの直し案を作り、利用者が承認したら自分のスキル集に入れる。
