起動時に新版を確認し、利用者が自動更新を有効にしていれば、会話や承認を中断しないタイミングで署名済み APK に更新する。Android が確認を求める場合は、アプリの更新画面からシステムの確認画面へ進める。

## 現状

「接続設定」の「更新を確認」から手動で確認し、利用者の操作で APK を取得する。アプリが SHA-256、パッケージ名、`versionCode` を照合した後に Android のインストーラーを開く。GitHub のローリングプレリリース `android-beta` に APK と `android-latest.json` を置く。アプリの更新 URL は初期状態では空欄で、自前の HTTPS 更新先も入力できる。tailnet 内では署名済み APK を個別に渡す運用もできる。 [Android の配布と更新](../../android/README.md#配布と更新) · [インストール・更新の設計](install-and-update.md#更新の操作とサーバーからの配布)

## 配布元とチャネル

- デスクトップと同じように、配布チャネルで更新候補を選ぶ。`stable` は公開安定版、`beta` は既存の `android-beta` に対応するベータ版、`dev` は自前サーバーで明示的に公開した開発版を対象とする。チャネル間で同じ `applicationId` とリリース鍵を使う成果物には、全チャネルで単調増加する `versionCode` を割り当てる。チャネル変更後は、選択先が端末より新しい版を出した時点で更新できる。
- GitHub に加えて、接続先の自前の secretaire から Tailscale 経由で取得できるようにする。チャネルごとに `android-latest.json` と、その `apk` 欄で指定する署名済み APK を同じ URL ディレクトリに置く。JSON は GitHub と同じ形式（`version`、`versionCode`、`package`、`sha256`、`apk`、`minimum_protocol`、`release_notes_first_line`、`built_at`）を使う。
- 自前サーバーが提示する候補は、稼働中のサーバーと対応プロトコルの範囲が重なる APK に限る。`minimum_protocol` は現行 JSON の下限として維持し、公開時に APK の対応上限もサーバー側の登録情報で照合する。確認用 HTTP は WebSocket の接続・プロトコル交渉前にも利用できる。
- `stable` と `beta` では設定したチャネルの自前サーバーを優先する。自前の配布元に到達できない場合に GitHub で取得できる候補は、同じチャネルで互換性を確認できる版に限る。互換候補なし、認証拒否、検証失敗は理由を表示し、その確認を終了する。稼働サーバーとの互換性を確かめられない場合は手動確認に回す。`dev` の取得先は自前サーバーとする。
- リリース処理は検証済み APK を版ごとの URL に登録し、取得可能になってから JSON をアトミックに切り替える。同じ版の APK の内容は固定し、更新中の端末が旧 URL から再開できるよう直前の正常版を保持する。公開に失敗した場合は直前のフィードで配信を続ける。

自前サーバーのフィードと APK は同じ認証で保護する。tailnet 内の取得は許可リストと Tailscale の接続元 ID を確認し、最初の実装では tailnet 側も HTTPS を使う。tailnet 外から自前サーバーに接続する場合は HTTPS と端末トークンを必須にする。トークンは既存の暗号化保存を使い、設定した自前サーバーのオリジンに限って Bearer ヘッダーで送る。リダイレクト先も HTTPS に限定し、別オリジンや GitHub にはトークンを送らない。URL、アプリとサーバーのログ、診断出力にトークンを残さない。 [リモート接続](../../docs/remote.md)

## 取得とインストール

1. 自動更新は利用者が設定で有効にする。起動時と、作業が終わって操作が落ち着いたときに、前回の確認時刻と再試行間隔を見てフィードを確認する。手動確認も同じ取得・検証処理を使う。
2. 新版をアプリ専用領域の一時ファイルに取得する。切断時は URL、期待ハッシュ、HTTP の検証子が同じ場合に `Range` / `If-Range` で再開し、表現が変わった場合は先頭から取り直す。完全な APK の SHA-256 を JSON と照合し、APK の署名を検証して、署名証明書をインストール済みアプリの証明書と照合する。APK、フィード、稼働中のアプリで `applicationId` が一致し、APK の `versionCode` がフィードと等しく、端末の値を厳密に上回ることを確かめる。
3. 進行中の作業カード、作業の詳細、判断待ちの承認が画面に出ている間、応答中、編集中、送信・添付中は適用を保留する。起動時も復元済みの画面状態と作業・承認の状態を確かめた後に適用する。再接続中など、その状態が分からない間は待つ。`PackageInstaller` セッションのコミット直前にも条件とインストール済みの版を再確認する。接続設定と下書きはプロセスの入れ替え前に保存する。
4. Android 12 以降は fuzukue 自身をインストーラーとして `PackageInstaller` セッションを作り、`USER_ACTION_NOT_REQUIRED` を指定する。マニフェストに既存の `REQUEST_INSTALL_PACKAGES` と `UPDATE_PACKAGES_WITHOUT_USER_ACTION` を宣言し、`canRequestPackageInstalls()` で「この提供元のアプリを許可」の状態を確認する。利用者はこのアプリの提供元許可を初回に設定でき、後から取り消せる。自己更新、既存のインストーラー（installer of record）が同じ場合、更新所有者が同じ場合の扱いや、APK の対象 SDK の下限は Android の判定に従う。 [PackageInstaller の条件](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int)) · [提供元の許可](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls())
5. `STATUS_PENDING_USER_ACTION`、提供元の許可がない場合、Android 10 / 11 では、更新状態を表示して利用者の操作を待つ。必要に応じて提供元の設定を案内し、許可を確認してからシステムのインストール確認へ進む。承認や作業の画面に確認画面が割り込まないよう、アプリが前面にあるときに利用者が更新画面から開く。その時点でも作業と承認の状態を確認する。

## 失敗からの復旧

- 通信切断や容量不足には、理由と再試行手段を表示する。破損、署名・ID・版の不一致は候補を破棄する。キャンセルやインストール失敗では有効な APK を再試行用に保持できる。未完了のセッションを照合し、不要になったセッションと一時ファイルを整理する。
- プロセス終了やパッケージ置換をまたいで処理結果を確認できるよう、セッション ID と候補の `versionCode` を保存する。次回起動時に実際のインストール済みの版を確認し、接続と作業状態を復元する。キャンセルや OS の拒否の直後は利用者の操作を待つ。
- サーバーには最後に正常動作を確認した APK を保持する。端末では、取得済みの直前の正常版があれば、再確認用にアプリ専用領域に 1 世代分を残す。適用後に不具合が見つかったら問題版の新規配信を止める。通常の Android 更新では低い `versionCode` へのダウングレードはできない。復旧版は、直前の正常版相当のソースまたは修正版を、問題版より高い `versionCode` と同じ `applicationId`・署名鍵で再ビルドして配布する。復旧版が問題版の保存データを読めることも確認する。

## 実機で確かめること

- Android 10 / 11、12、現在の対象 OS の端末で、GitHub やファイル管理アプリから入れた署名済み APK の初回更新と、fuzukue 自身をインストーラーとする次の更新を試す。OS、機種、APK の対象 SDK、インストール元、更新所有者、提供元許可の有無・取り消し、確認表示と結果を記録する。
- GitHub と Tailscale の自前サーバーを切り替え、tailnet 外の HTTPS と端末トークン、プロトコル不一致、回線切断と再開、署名違い、古い版、容量不足、システム確認のキャンセルを試す。
- 作業カードや承認の表示中、下書き入力中、再接続中の保留と、起動時・アイドル時の適用を試す。更新後に接続設定・下書きが残り、再接続で作業状態と承認を再表示できることと、より高い `versionCode` の復旧版へ更新できることを確かめる。

## 決めること

- 既存の手入力 URL とチャネル設定の移行、初期チャネル、GitHub への切り替えを利用者に知らせるタイミング。
- `stable` の公開条件、`dev` の版番号割り当て、署名鍵の交代手順と許容する署名履歴。
- アイドルとみなす時間、確認・再試行間隔、従量回線での取得、手元と配布元での APK の保持期間。
- APK の互換性情報の登録方法と、WebSocket に接続できない端末が GitHub 候補の互換性を判断するための情報源。
