# 完全承認モード

完全承認モードは、作業役を Claude Code や Codex の全面許可設定と同じ感覚で使うための、ワークスペース単位の設定。既定は無効。有効化すると、新しく起動する作業役の既定の実行範囲が `full-access`、承認方針が `never` になる。ネイティブのシェルとファイル編集、ネットワーク、`git push` などを OS ユーザーの権限で実行できる。通信先のサービスや Git のリモートが求める認証・アクセス権は別途必要になる。

## 有効化・確認・停止

端末トークンまたはサーバー共有トークンで認証したクライアントで対象ワークスペースを選び、次のコマンドを受付に送る。サーバーが処理し、モデルには転送しない。

| コマンド | 動作 |
| --- | --- |
| `/full-approval` または `/full-approval 24h` | 24 時間有効にする |
| `/full-approval 1h`、`/full-approval 8h` | 指定した時間だけ有効にする |
| `/full-approval until-disabled` | 停止するまで有効にする |
| `/full-approval status` | 有効状態と期限を表示する |
| `/full-approval off` | 停止する |

同じ認証で `GET /settings/full-approval?workspace=<workspace-id>` を呼ぶと、現在の設定、監査、過去 24 時間のツール別の件数を取得できる。変更には同じパスへ JSON を POST する。

| JSON | 動作 |
| --- | --- |
| `{"mode":"full"}` | 既定の 24 時間で有効にする |
| `{"mode":"full","duration":"until_disabled"}` | 停止するまで有効にする |
| `{"mode":"off"}` | 停止する |

有効化すると、承認キューに残っている対象の依頼と、稼働中の作業役が待っている対象の依頼も `full_mode` として承認する。待機中の処理には元の依頼への応答を一度だけ届ける。利用者の判断と競合した場合は、先に確定した判断が有効になる。サーバーが有効な設定を復元したときも、永続キューの対象を承認する。フォルダーの読み取り依頼は 1 時間の許可に変わり、元の読み取りは再試行できる。サーバー制御の操作や、既存の方針で個別承認が必要な受付の操作は引き続き確認を待つ。

停止・期限切れで、新たな完全承認を止める。確定した許可はそれぞれの有効期限まで使える。その有効期間に起動した作業役へ停止を要求し、続ける場合は新しい作業役を起動する。既に発生した副作用や切り離されたプロセスは別途扱う。期限を設定し直す場合も、前の有効期間は終了する。ワークスペース画面での常設表示とワンタップ停止は R-73 で扱う。

## 作業役の実行範囲

`GET /settings/worker-execution?workspace=<workspace-id>` で保存値（`settings`）、次の起動に適用する値（`effective`）、bubblewrap の検査結果（`bubblewrap`）を取得する。同じパスに `{"sandbox":"workspace-write","approval":"ask"}` のような JSON を POST すると設定を置き換える。`{}` で既定の起動経路に戻る。

| `sandbox` | ファイルシステム |
| --- | --- |
| `read-only` | ホストを読み取り専用で見せ、ジョブ専用の一時領域だけに書き込める |
| `workspace-write` | 上記に加え、作業ディレクトリに書き込める。個別の MCP 操作は、引き続きツールの範囲や事前条件を検査する |
| `full-access` | ホストの OS ユーザーが持つ権限で実行する |

`approval` はネイティブの承認を `ask`（利用者に確認）、`auto`（作業役の要求へサーバーが応答）、`never`（バックエンドの確認を省略）から選ぶ。完全承認モード中は `never` を適用し、明示された `sandbox` はそのまま使う。OS の書き込み制限は承認を省いても適用される。モードを停止すると保存された起動設定に戻り、保存値もない場合は従来の作業役設定を使う。

### bubblewrap の検査

サーバープロセスと同じアカウントで、実行ファイルの有無、非特権ユーザー名前空間、最小ルートでのコマンド起動、許可先への書き込み、範囲外の書き込み拒否、任意のネットワーク名前空間を検査する。サーバープロセスの存続中は最初の結果を時刻（`checked_at`、Unix ミリ秒）とともに保持する。失敗時には失敗した検査と stderr を返す。

WSL2 の試行では `unshare --user --map-root-user` は成功したが、bubblewrap のマウントが `bwrap: Failed to mount tmpfs: No such file or directory` で失敗した。検査に失敗した場合、明示的な `read-only` と `workspace-write` の起動はエラーになる。`full-access` は bubblewrap の検査結果にかかわらず利用できる。設定変更後にホストの状態を再検査するにはサーバーを再起動する。作業役の API とループバック MCP への接続に使うネットワークは、両サンドボックスでもホストと共有する。

## 設定と監査の境界

設定ルートは端末用資格情報を要求する。作業役の MCP キーは自身のジョブで許可されたツールに使え、サーバーの設定や受付専用ツールには使えない。自己更新やロールバックは受付の操作経路にある。設定ファイルはサーバーが権限 `0600` で原子的に置き換え、起動中はサーバーが保持する状態を使う。同じ OS アカウントで `full-access` を使うと、シェルからこのアカウントの状態ファイルを書き換えられる。完全承認モードは、作業役を隔離するセキュリティ境界ではなく、個別確認を省いて監査を残す機能である。

サーバーが自動承認した依頼は、承認 ID、時刻、スレッド、ジョブ、ツール名、範囲、リスクを `granted_by=full_mode` で記録する。バックエンドが承認 RPC を送らず直接実行する場合は、通知されたネイティブ操作を記録する。返却する監査では引数をマスクする。稼働中の呼び出しに対する承認と一回限りの消費は一つの保存操作で行う。停止・再有効化やサーバーの再起動をまたいでも、依頼元と操作が同じ承認履歴を参照し、処理の再実行を防ぐ。実行結果が不明な場合は、その結果を照合してから再試行する。

フォルダーの読み取りに発行した 1 時間の許可には個別の有効期限と撤回がある。受付が行う操作については、通常の push や公開・自己更新などの既存の個別判断を維持する。朝の報告での集計は R-63 を参照。
