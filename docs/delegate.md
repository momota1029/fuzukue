# 作業役の並行実行と待機理由

グローバルな開始枠は一つのサーバー内で全ワークスペースが共有します。既定では 4 件まで、変更予定の重複や不明な変更予定に関係なく開始できます。4 件以上が枠を使っている間は、変更予定が分かり、実行中のどの作業とも重ならない依頼を最大 12 件まで開始します。枠を使うのは開始を許可された委譲ジョブです。CPU 負荷と空きメモリ、更新のための Draining、使用量による一時停止も開始を制限します。

ソフト上限を超える並行実行には、`delegate` の `touches` にワークツリー相対のパスまたは glob を明示できます。空配列は読み取り専用の宣言です。省略すると依頼文のパス、次いで同じスレッドの直近の委譲を参照します。

長期目標の並行数設定は、スレッド内で同時に実行できるジョブの上限と開始間隔を調整します。使用量に余裕があるときの上限は「全力」が上限なし、「標準」が既定で 2 件、「節約」が既定で 1 件です。「節約」は方針の更新間隔も長くし、使用量を抑えます。使用量が高いときは「標準」と「節約」の上限が 1 件になります。「全力」でもサーバー全体の枠と使用量による一時停止は適用されます。

進行中の方針では、同じ目標を指定した `plan` または `replan` の `pace` に `full`、`normal`、`economy` を渡すと、履歴と次の手順を保ったまま並行数設定を変更できます。


作業役にスレッド外の資料の読み取りを渡すときは、`delegate.folder_grants` に有効な許可 ID を明示します。 [フォルダーの読み取り許可](folder-grants.md)

## ジョブの名前と一覧

`delegate` の `title` と任意の `label` は、利用者の言語で表示幅 40 桁（全角 20 字、半角 40 字相当）以内にします。背景、変更対象、制約、完了条件は `prompt` に書きます。表示名の省略時は題名から名前を作り、先頭に `R-81` のようなカード ID があれば別に表示します。長い名前は省略記号付きで表示し、題名や短縮前の名前は詳細に残します。ツール結果の `label_shortened` で短縮を確認できます。

デスクトップではチャット下部の作業状態、完了後は「ジョブ」を開くと、表示名、モデル、思考レベル、段階、バックエンド、時間、ツールの使用状況が見えます。同じ場所で改名、ID のコピー、実行中の連絡・停止、完了報告の表示ができます。受付から改名する場合は `rename_job` にジョブ ID と `label` を渡します。改名は受付とデスクトップに反映され、変更前後の名前と時刻をジョブの記録に保存します。

運用上さらに短くしたい場合は、サーバーで受付に読み込ませる指示ファイル（通常は `~/AGENTS.md`、`FUZUKUE_USER_INSTRUCTIONS` で指定可能）に「委譲の題名と表示名は表示幅 24 桁（全角 12 字）以内。詳しい依頼は prompt へ」のようなルールを追加します。これは受付が名前を付けるときの指示で、サーバーが短縮する上限は 40 桁です。

## ファイルの読み取り・検索・一覧

シェルで `head`、`tail`、`sed -n`、`cat` を使う場面では `fs_read` を使えます。たとえば `{"path":"build.log","tail_lines":30}` は末尾 30 行を返します。先頭は `{"path":"build.log"}` で最大 400 行、`end_line: 20` で 20 行までに絞れます。行番号は 1 始まりで両端を含みます。 `start_line: -5` は末尾から数えて 5 行目で、`end_line` は先頭からの行番号で指定します。 `tail_lines` は 1〜400 に丸め、範囲指定と併用できません。

`fs_read` の出力は最大 400 行、本文は最大 64 KiB です。ファイル全体が 16 MiB の走査上限内なら `total_lines` を返します。上限を超えるファイルは先頭からの範囲を読み取れますが、末尾からの指定には全体の読み取りが必要です。続きがある場合は `next_start_line` を次の呼び出しに渡せます。

### `fs_search` と `rg` / `grep`

`paths` には検索起点を最大 16 件指定できます。`path` も渡した場合は先に検索します。結果は起点順にまとまり、各パスに起点が付きます。`max_results` と `sort` は起点ごとに適用され、バイト数と時間の上限は検索全体で共有します。いずれかの起点で上限により結果を省略した場合は `truncated: true` を返します。

`fs_search` はディレクトリを既定で再帰検索します。例として `{"path":"src","pattern":"TODO","types":["rust"],"context":2}` は `rg -t rust -C 2 TODO src` に相当します。パターンの先頭が `-` の場合も `pattern` にそのまま渡せます。 `patterns` は複数の `-e` に相当し、いずれかに一致する行を選びます。 `rg -S` は `smart_case: true` で、パターンに大文字を含む場合は大文字と小文字を区別します。 `ignore_case: true` を同時に指定した場合は常に区別しません。

| フラグ | 引数 |
| --- | --- |
| `grep -r` / `-R` | ディレクトリを再帰検索。走査中に見つけたシンボリックリンクはたどりません。 |
| `-n` / `-i` | `line_number: true`（既定） / `ignore_case: true` |
| `-l` / `grep -L` / `-c` | `output_mode: "files_with_matches"` / `"files_without_matches"` / `"count"` |
| `-E` / `-F` | 正規表現が既定 / `fixed_string: true` |
| `-v` / `-w` / `-x` | `invert: true` / `word: true` / `whole_line: true` |
| `-A` / `-B` / `-C` | `after_context` / `before_context` / `context` |
| `-m` | ファイルごとの `max_count` |
| `--include` / `--exclude` / `--exclude-dir` | `globs: ["*.rs","!sample.rs","!fixtures/"]` |
| `-o` / `-h` / `-H` | `only_matching: true` / `with_path: false` / `with_path: true` |
| `-q` | `output_mode: "count"` と `max_results: 1`。一致があれば集計行が返ります。 |
| `rg --files` | `output_mode: "files"`。パターンを省略し、ファイル内容を読み取らずパスを返します。 |
| `rg -t` / `-T` | `types` / `exclude_types`。例は `rust`、`ts`、`md`、`py`、`toml`、`kt`。 |
| `rg --column` / `--sort modified` / `--stats` | `column: true` / `sort: "modified"` / `stats: true` |
| `rg --hidden` / `--no-ignore` | `include_hidden: true` / `include_ignored: true` |

`glob` を先に評価し、`globs` の最後に一致した規則を適用します。先頭が `!` の規則は除外します。通常は読み取り範囲内の `.gitignore` と `.ignore` を適用します。 `target`、`node_modules`、`build`、`dist` などの生成先を検索するときは `path` に明示します。Git の内部データや保護対象は読み取り範囲外です。

`before_context` と `after_context` は指定した側の `context` を上書きし、各値は 0〜5 に丸めます。 `max_count` は指定時に 1〜100,000、`max_results` は 1〜200 に丸めます。 `column` は 1 始まりのバイト位置を返し、`invert` では `null` を返します。 `only_matching` は空でない一致部分を個別の行として返します。複数行の検索には `multiline: true`（`rg -U`）を指定します。一致範囲はファイル内に収まり、通常の本文出力には最初と最後の行番号が付きます。複数行モードの `count` では、同じ行を共有する一致範囲を一つに数えます。 `grep -P` の先読み・後読み・後方参照を使う式は、周辺の文字を消費する式や前後の行を含む検索に置き換えられます。

本文検索は 1 MiB 以下の UTF-8 ファイルを合計 32 MiB まで読みます。一覧と本文検索は最大 64 階層、20,000 項目、5 秒を目安に打ち切ります。 `stats` は検索した UTF-8 ファイル数、一致したファイル数、本文の読み取りバイト数、経過ミリ秒を返します。 `truncated: true` のときは、表示または検索の上限に達しています。

### `fs_list` と `ls` / `find`

`max_results` またはその別名の `limit` で返す項目数を指定できます。既定値は 500 で、範囲外の整数は 1〜500 の最寄りの境界値に丸めます。両方を同時に指定することはできません。

`fs_list` は `ls`、`ls -R`、`find` の代わりに使えます。 `{"path":"src","recursive":true,"glob":"*.rs"}` は最大 64 階層から一致する項目のパス、種類、`size`（バイト）、`mtime_unix_secs`（Unix 秒）を返します。 `depth` で階層数を 1〜64 に指定でき、通常は直下の 1 階層を一覧します。

## ファイルの書き込みと終了時の照合

作業役は作業ツリーの編集に `fs_write`、`fs_edit`、`fs_apply_patch` を使います。受付からは編集するパスを `touches` で指定して委譲します。範囲内は承認なしで実行し、範囲外や変更予定が不明な場合は、作業ツリー内の変更に限って利用者が一件ずつ承認します。承認画面にはパス、変更後の SHA-256、差分の抜粋を表示します。承認待ちの間にファイルが変わった場合は書き込まず、読み直しを求めます。

三つの道具はいずれも、作業ツリー相対のパスと 4 MiB までの UTF-8 ファイルを扱います。一度の呼び出しで渡す `content`、`old`、`new` は各 256 KiB までです。足りない親ディレクトリは書き込み時に作成します。`..`、シンボリックリンク、ハードリンク、Git の内部データ、フォルダー許可と同じ保護パスは指定できません。

作業役は `list_tests` と `run_tests` で自分のチェックアウトのテストを検出して実行します。隔離コピーは `dir`、専用のビルドディレクトリと一時領域は `target_dir` と `tmp_dir` で指定します。承認の扱いは[完全承認モード](full-approval.md#作業役の実行範囲)を参照してください。

| 道具 | 入力と結果 |
| --- | --- |
| `fs_write` | `path` と `content`。一件を作成または上書きします。`append: true` では末尾に追加します。 |
| `fs_edit` | `path`、置換前の `old`、置換後の `new`。置換箇所が一意であることを検査し、置換後の文字列で適用済みと判断できる場合は変更しません。 |
| `fs_apply_patch` | `path` と単一ファイルの unified diff `patch`（768 KiB まで）。ヘッダーは `--- a/<path>` と `+++ b/<path>`、作成時の変更前ヘッダーは `--- /dev/null` を指定します。 |

書き込み結果には差分、変更後の SHA-256、変更の有無、書き込んだ場合は監査 ID が含まれます。受付は `job_write_audit` に完全なジョブ ID を渡し、新しい順に監査を読めます。記録には操作名、パス、変更前後のハッシュ、範囲外の承認の有無、書き込み結果が残ります。監査ファイルはサーバーの状態ディレクトリに保存され、ジョブ一覧の保持期間を過ぎてもジョブ ID で取得できます。`pending` は結果の確定前に処理が中断された可能性を示します。

ジョブの完了時と停止時に、開始前後の作業ツリーを照合します。範囲外の変更があれば、報告の「範囲外の書き込み」にパスと処置を記します。変更予定が不明なら、観測した変更をすべて確認対象にします。コピー可能な通常ファイルはジョブの復旧領域 `delegate-recovery/<ジョブ ID の接頭辞を除く部分>/quarantine/` に保存します。上限はファイルごとに 32 MiB、ジョブ合計で 128 MiB です。保護対象、削除されたファイル、リンク、上限を超えたファイルは処置を一覧に記録します。Git の内部データとサーバー管理の作業ツリー内メタデータ（`.git`、`.fuzukue`、`.labo`、`threads/`）は照合の対象外です。

利用者や他のジョブと作業ツリーを共有できるため、前後の照合だけでは書き込み元を特定できません。追跡済みのファイルも自動では復元せず、作業ツリーを保持します。範囲外の承認を受けた変更も照合に残ります。報告から `manifest.json` をたどると全件を確認できます。

## デッキの節を査読する

`request_review` に掲載順の `cards` と `kind: "math"`、`"output"`、または `"both"` を渡します。講義の節は必要に応じて `section` で明示します。`"both"` は同じ時点の写しから数学の根拠と出力のビルド結果を準備し、両方の査読をまとめて受け付けます。依頼の応答には共通の `reviewed_version` と査読ごとの `session`、`input_hash` が含まれます。 [数学査読で辿る参照](graph.md#節の数学査読で辿る参照)

## ブラインド査読

序文だけを査読する、あるいは指示文だけで意図が伝わるか調べるには、`delegate` に `isolation: "blind"`、`backend`、API の `model`、`prompt` を指定します。`prompt` は原文のまま渡ります。比較では受付がファイルを読み、出所や元のパスを伏せた本文を `artifacts: [{"label":"A","text":"…"},{"label":"B","text":"…"}]` として添えます。成果物は空行と `[A]` のようなラベルに続けて、改行を含めた本文をそのまま渡します。

サーバーはテキストだけの API リクエストを 1 回送ります。査読役には作業ディレクトリ、ファイル、シェル、MCP、ウェブ検索、会話履歴、プロジェクト指示、スキルへのアクセスがありません。判定にはモデルの事前知識、提供元の指示や安全ポリシー、本文中の手がかりが影響し得ます。

`backend: "codex"` は OpenAI Responses API（サーバー環境の `OPENAI_API_KEY`）、`backend: "claude"` は Anthropic Messages API（`ANTHROPIC_API_KEY`）を使い、それぞれの API 利用枠で実行します。受付は返答の本文を原文のまま受け取り、ジョブの記録には `isolation: "blind"`、バックエンド、モデルが残ります。


## 設定

`~/.config/fuzukue/server.toml` に `[delegate]` を記述します。サーバーの起点に指定したワークスペースの `fuzukue.toml` にも同じ節を書けます。起点の設定はキーごとにサーバー設定を上書きし、結果はサーバー全体で共有します。どちらも起動時に読み込むため、変更の反映にはサーバーの再起動か、再起動を伴う自己更新が必要です。

| キー | 既定値 | 内容 |
| --- | ---: | --- |
| `max_parallel` | 4 | 変更予定に関係なく確保できる枠の上限 |
| `max_parallel_hard` | 12 | 並行実行の最大数 |
| `goal_normal_running` | 2 | 使用量に余裕があるときの「標準」のスレッド内上限 |
| `goal_economy_running` | 1 | 使用量に余裕があるときの「節約」のスレッド内上限 |
| `max_load_per_cpu` | 1.5 | サーバープロセスから利用できる論理 CPU 数に掛けた 1 分間負荷の上限 |
| `min_available_memory_mib` | 4096 | 開始に必要な空きメモリの下限（MiB） |
| `usage_reroute` | `true` | 使用量に応じて順番待ちの作業のモデルを自動で切り替える（Claude と Codex の間を含む） |
| `usage_pacing` | `true` | 使用量がリセット前に尽きる見込みのときに、保留・並行数の削減・段階の引き下げを行う |
| `usage_pacing_from` | 0.7 | 見込みを判断に使い始める使用率（0〜1） |
| `usage_pacing_running` | 1 | 見込みが尽きる側のバックエンドで同時に実行する作業数 |

20 論理 CPU を利用できるサーバーの設定例です。

```toml
[delegate]
max_parallel = 8
max_parallel_hard = 16
max_load_per_cpu = 1.5
min_available_memory_mib = 4096
```

### 使用量に応じた経路の切り替え

**この切り替えは既定で有効です。依頼やスレッドでモデルを固定していない作業は、Claude と Codex の間でも自動で移ります。** 依頼文や作業内容を送る先の事業者が変わるため、片方だけを使いたい場合は、`fuzukue.toml` か `server.toml` で止めて、サーバーを再起動します。

```toml
[delegate]
usage_reroute = false
```

`usage_reroute = false` では、モデルと段階の選び方、長期目標の一時停止が、この機能を入れる前の動作に戻ります。`tiers.models` の並びで使用量の多いモデルを飛ばす動作と、使用率が 90% 以上のときや「節約」で段階を一段下げる動作は残ります。この状態の段階の引き下げには、下に挙げる作業の保護は適用されません。尽きる見込みによる保留と並行数の削減は `usage_pacing` で別に指定します。使用率 90% 以上での引き下げも止める場合は `usage_pacing = false` を指定します。

順番待ちの作業は、使用量が変わるたび、また少なくとも 60 秒ごとに行き先を見直します。実行中の試行は止めず、受付の会話も保留しません。段階を上げる再試行は、いったん枠を返して同じ方法で行き先を選び直し、開始の条件と並行数の確認を通ってから始めます。再試行の段階は下げません。一時停止のしきい値は従来のままです。

待っている再試行は、作業の一覧で `waiting` と表示します。開始の直前には、初回と同じくスレッド、方針の手順、作業役の許可を確かめ、満たさなければ再試行せずに終えます。利用者が目標を一時停止している間は始めません。更新の準備中でまだ新しい作業を受け付けている間は、方針の手順の再試行も続けます。更新や終了の排出が受付を閉じた場合は、再試行せずに中断した作業として記録し、再開前の確認に回します。その排出を後で取り消しても同じです。

- **一時停止中:** 割り当て先のバックエンドが一時停止中なら、同じ段階の別のモデルに空きがあれば切り替えます。同じ段階に候補がなければ、段階を下げられる作業は一段下の候補に切り替えます。候補がない場合に限り、リセットを待ちます。
- **尽きる見込み:** 使用率が `usage_pacing_from` 以上の枠で、最近の消費ペースがリセット前の使い切りを示す状態を指します。空きのある別のモデルがあれば切り替え、なければ段階を下げられる作業は一段下げます。段階を下げられない場合、急ぎの作業は `usage_pacing_running` 件まで実行し、急ぎでない作業は保留します。
- **見込みの解除:** 行き来を繰り返さないよう、直近の判定から 10 分以上たち、残量がリセットまでの時間の 1.25 倍以上持つと見込まれる場合か、消費ペースの見積もりが 15 分以上得られない場合に解除します。枠がリセットされた場合も解除します。

`usage_pacing` が有効なら、一時停止前でも使用率が 90% 以上のバックエンドに割り当てた作業は、段階を一段下げます。

急ぎの作業は、受付が依頼した作業です。方針の手順や作業役からの依頼は急ぎではありません。長期目標の「全力」では尽きる見込みによる保留と引き下げを行わず、一時停止中の切り替えと、上の 90% での引き下げを行います。「節約」では段階を一段下げます。

次の作業は段階を下げず、必要なら待ちます。`min_tier` に `standard` 以上を指定した作業、`tier: "heavy"` を指定した作業、不可逆な操作を含む作業、依頼文がセキュリティ、アーキテクチャや設計判断、横断的な変更、証明・形式化に触れる作業です。「節約」と 90% での引き下げも対象外です。同じ段階の別のモデルへの切り替えは行います。

依頼で指定したモデル、スレッドで固定した作業役のモデル（名前のある作業役に適用される場合を含む）、役割ごとに上書きしたモデルは置き換えません。尽きる見込みや一時停止に当たれば、上の急ぎ度に従って実行するか待ちます。

切り替え先は、サーバーの状態ディレクトリにある `agent-settings.json` の設定から選びます。順に、段階ごとのモデル（`tier_models`）、`tiers.models` の並び、役割の `fallbacks` です。役割の `fallbacks` は light の候補にだけ使います。standard や heavy の作業が移る場合は段階の引き下げになり、切り替えの理由にもそう表示します。ある段階の `tiers.models` が空なら、次の組み込みの候補も使います。組み込みの候補は、このサーバーで使用量を受け取ったことがあるバックエンドに限ります。`tiers.models` に並びを書くと、その段階の組み込みの候補は使いません。

| 段階 | Claude | Codex（思考レベル） |
| --- | --- | --- |
| light | `claude-haiku-5-5` | `gpt-6.1-terra`（low） |
| standard | `claude-sonnet-5-5` | `gpt-6.2-sol`（medium） |
| heavy | `claude-opus-5-5` | `gpt-6.2-sol`（high） |

切り替えた理由はジョブの詳細の段階の理由と、`list_jobs`・`job_status` の `routing_note` に出ます。保留の理由は「待機中」に出ます。別のモデルへの切り替えを止めるには `usage_reroute = false`、保留・並行数の削減・使用量による段階の引き下げを止めるには `usage_pacing = false` を指定します。

状態欄の詳細を開くと、各ジョブの「待機中」に、通常・最大枠、重なるパスと相手の作業名、負荷、スレッドの並行数上限など、その時点で開始を止めている理由が表示されます。受付は `list_jobs` で同じ理由と最近の動きを読み、`job_status` で個別の報告を確認できます。稼働中のサーバーは終了済みのジョブを直近 256 件まで保持します。稼働中の変更一覧は観測できた書き込みで、終了時には同じワークツリーで並行して行われた変更が差分に含まれることがあります。

`list_jobs` の変更ファイル一覧は、`.gradle`、`build`、`target`、`.kotlin`、`node_modules` の各ディレクトリ内を除いた先頭 8 件と総数を返します。`job_status` では `view: "report"` で完了報告と変更の要約、`view: "summary"` で変更の要約を、どちらも状態や時刻と合わせて取得できます。既定の `view: "full"` では入力の抜粋、直近の動き、変更ファイルなども取得できます。応答の一部を省略した場合は `truncated: true` が付きます。

### ツール呼び出しの上限

`~/.config/fuzukue/server.toml` の `[tool_guard]` で上限を変更できます。正の整数を指定し、サーバーを再起動すると反映されます。

```toml
[tool_guard]
same_tool_per_minute = 300
total_calls = 2000
```

作業役の試行ごと、受付のターンごとに、同じツールの直近 60 秒間の呼び出し数と全ツールの合計を数えます。Fuzukue の MCP 呼び出しはコード内から発行されたものも数えます。バックエンドから観測できるツール操作も対象です。

どちらかの上限を超えると、その試行やターン中の後続の MCP 呼び出しをエラーで返します。バックエンド側で許可を求められたツール操作も拒否します。作業役がさらに 8 回呼び出した場合は試行を停止し、作業ツリーと途中経過を残してスレッドに通知します。受付には上限を超えた時点で通知し、会話は続けられます。

## 報告の配信待ちと復旧

受付専用の `desk_queue` には、保留 ID、種別、引き取り状態、確認理由、スレッド ID、記録時刻が分かる場合は経過秒が出ます。`job_ids` に完全なジョブ ID を渡すと、各項目に記録された関連 ID を照合できます。`offset` と `limit` でページを指定できます。確認理由にはサーバーが定めた短い文言を使います。

報告、Claude の保留入力、委譲が確認待ちや再試行待ちにある場合は、配信の状況を確認し、利用者の了承を得てから `desk_redeliver` に保留 ID と `confirm: true` を渡します。サーバーは同じレコードを待機状態へ戻し、通常の配信処理で再評価します。

相手の切り替え待ちなど、報告や Claude への保留入力がターン送信前に止まった場合、サーバーは同じ保留レコードを再試行します。待ち時間は 1、2、4、8、16、最大 30 秒で、再起動をまたいで保持されます。送信準備中にサーバーが停止した場合、起動時にレコードを一度だけ待機状態へ戻します。ターンを送信した可能性があり、結果を確認できない場合は、本文と理由を確認用に保存します。報告の配信待ちが最初の拒否から 5 分に達すると、`job_status` の `stalled_report_deliveries` に保留 ID、待機秒数、再試行回数、直近の拒否理由、次の試行時刻（Unix ミリ秒）が出ます。

### 旧バージョンで止まった報告の一回限りの移行案

旧バージョンで記録された報告は、移行対象の保留 ID を個別に確認します。候補は `held-work.json` にある `Desk` の `Report` のうち、`claimed: true` かつ確認理由が「相手を替えるには Claude のターンの完了を待つ」と完全一致するものです。当時の実装でこの理由がターン送信前のガードから記録されたことと、対象のスレッド・バックエンドの記録に同じ報告の送信や返答がないことを照合します。証拠が足りないものは確認待ちに残します。

実施する場合は、サーバーの停止中にジャーナルのバックアップと対象 ID の一覧を作り、コピー上で差分を確認します。承認した ID が候補条件を満たす場合に限り、`claimed` を `false` にして `review` を除きます。ID、スレッド、報告本文は保持し、ファイル全体を原子的に置き換えます。条件から外れたレコードは再実行時にもスキップされます。修正版の起動後、対象 ID ごとに送信と受付の返答が一度だけ記録されたことを確認します。

## 作業役からの承認

会話の入力欄で、承認モードの隣にある「作業役の承認」を選びます。設定はワークスペースごとに保存され、既に保留されている承認は会話から操作できます。初期値はサーバーが管理するワークスペース別の状態ディレクトリ（通常は `~/.local/state/fuzukue/<ワークスペース>/`）に置いた `fuzukue.toml` から読み込みます。デスクトップで変更すると、同じディレクトリの `worker-approval-policy.json` が優先されます。委譲先の作業ツリーに置かれた設定ファイルや作業役の MCP ツールからは、この設定を変更できません。

```toml
[delegate]
worker_approvals = "ask"
```

| 値 | 承認の扱い |
| --- | --- |
| `ask`（既定） | 利用者が 1 件ずつ判断します。ただし検査を通った `pwd`、`ls`、`cat`、`sleep` だけの Bash と、ジョブ用一時領域の自分のファイルだけを読む Bash はサーバーが許可します。 |
| `advisor` | 検査を通った Bash はサーバーが許可します。対象の `Read` は方針役に諮ります。応答の上限は 25 秒です。拒否や利用者への引き継ぎも選べます。失敗や不正な返答の場合は、利用者が判断します。 |
| `auto` | サーバーの検査を通った対象の承認を自動で許可します。 |

Claude の `Read` で自動の判断を受けられるのは、割り当てられたワークツリー内の通常ファイルです。シンボリックリンクとハードリンクは対象外です。ジョブ用一時領域にある作業役自身のファイル（バックグラウンドで実行したコマンドの出力など）は、どの設定でも確認なしで読めます。一時領域の直下にあるドットで始まる項目（バックエンドのログイン情報の写しなど）は対象外です。作業役への指示では、ファイルはシェルの `cat` ではなく `Read` や `fs_read` で読むよう伝えます。

Linux では、Claude の `Bash` をサーバーが引数まで検査します。`pwd`、`ps`、`ls`、`cat`、`grep` などの読み取り専用の呼び出しを、許可したオプションと組み合わせた場合に対象になります。`|` と `&&` はすべての段を検査します。相対パスの起点は割り当てられたワークツリーです。検査を通った `cd` に続く段は、その移動先から解決します。ファイル引数はワークツリー、読み取りルート、またはジョブ用一時領域に限ります。一時領域はサーバーの状態ディレクトリの中にありますが、許可するのは一時領域内の作業役自身のファイルだけで、状態ディレクトリの他のファイルと一時領域直下のドットで始まる項目は対象外です。`sleep` は秒数だけを受け付けます。`rg` の本文検索には明示したファイルが必要で、一覧取得には `rg --files --no-ignore` を使えます。パス展開、リダイレクト、任意のスクリプト、Git コマンド、ビルド・テストは利用者の確認に回ります。

受付の Claude では、入力欄の「すべて自動」と編集の自動許可モードで、同じ Bash 検査を使います。作業役の設定は受付に影響しません。`file_inbox` と人の判断が指定された要求は利用者が確認します。

シェルの承認では、Fuzukue の設定・状態、作業範囲外の書き込み、読み取り専用領域への書き込みや実行、コミット・プッシュ、外部通信、サービスの登録・削除、一時領域外の破壊的な削除、サーバーの再起動・入れ替え、GitHub への書き込み、公開・署名は自動許可の対象外です。Claude のフックは OS の隔離機構ではありません。作業役の Codex にはワークツリー・一時領域と読み取りルートを指定し、ネットワークと昇格要求を無効にした実行プロファイルを渡します。Codex から承認要求が届いた場合は、利用者が確認します。

判断は承認 ID 1 件に限られます。利用者が先に応答した場合はその判断が使われます。自動の許可・拒否は判断者と理由を会話の詳細に残し、Bash では一致した検査規則も記録します。利用者に引き継いだ承認は、再接続後も操作でき、応答先が生きている間は自己更新の待機対象になります。

## Git の読み取り

受付と作業役は、承認済みの MCP ツール `git_read` で Git の状態を調べられます。作業役は割り当てられたチェックアウト、受付は現在のワークスペースが対象です。シェルから実行する Git コマンドには、従来の承認規則が適用されます。

たとえば現在のブランチは `{"subcommand":"rev-parse","args":["--abbrev-ref","HEAD"]}`、リポジトリのルートは `{"subcommand":"rev-parse","args":["--show-toplevel"]}`、ファイルを絞った差分は `{"subcommand":"diff","args":["--","src/main.rs"]}` で調べられます。

対応する操作は `rev-parse`、`status`、`log`、`diff`、`show`、`ls-files`、`ls-tree`、`cat-file`、`merge-base`、`describe`、`branch --list`、`tag --list`、`remote -v`、行範囲付きの `blame`、一部のキーに限った `config --get` です。`git show --stat HEAD` に相当する照会は `{"subcommand":"show","args":["--stat","HEAD"]}` です。 `diff` でも先頭の引数に `--stat` を指定できます。使える引数はツールのスキーマで確認できます。パスは `--` に続けてリポジトリ相対のリテラルで指定します。

結果には `text`、`truncated`、`exit_code` が含まれます。出力の上限は 64 KiB、Git 照会の実行時間の上限は 5 秒です。照会はインデックスを更新せず、フックや外部差分ドライバーを実行しません。リモートの URL はスキームとホスト名だけを表示するか、全体を伏せます。設定の照会はインクルードを展開せず、リポジトリ共通のローカル設定を読みます。

### 作業役のコミット

分離したクローンまたは作業ツリーを割り当てられた作業役は、`git_commit_scoped` にメッセージとファイルパスを渡してコミットできます。

```json
{"message":"範囲を限定した変更\n\nCo-Authored-By: Example <contributor@example.invalid>\n","paths":["src/main.rs"]}
```

`paths` にはジョブの有効な `touches` に含まれるファイルを、作業ツリーからの相対パスで一つずつ挙げます。指定ファイルの作業ツリーにある内容を使い、指定外のステージ済み変更は保持します。範囲外のパスは拒否されます。範囲を広げる必要があるときは受付に承認を求めます。共有ワークスペース、シンボリックリンク、Git 内部や機密用のパスは対象外です。

作者とコミッターはサーバーが管理するワークスペース別設定ファイル `fuzukue.toml` の次の項目で指定できます。省略時はリポジトリ共通のローカル設定にある `user.name` と `user.email` を使います。二つが揃っていない場合はコミットを拒否します。

```toml
[delegate.git_commit]
name = "Example Contributor"
email = "contributor@example.invalid"
```

メッセージは 16 KiB までです。トレーラーを含む本文をそのまま使い、フックと署名の実行を抑止します。成功するとコミットとツリーの SHA、コミットしたファイルの一覧、監査 ID を返します。指定ファイルに差分がなければ `created: false` を返します。受付からは `job_write_audit` で記録を確認できます。

### 受付で作業役のパッチを取り込む

作業役から受け取ったパッチは、Bash の `git apply`、`git commit`、`git restore` の代わりに、受付専用の `git_integrate_patch` で取り込みます。

```json
{"patch":"target/job/change.patch","message":"取り込みの要約","allow_paths":["src/**","docs/delegate.md"]}
```

`patch` はワークスペース内の UTF-8 の差分ファイルです。上限は 768 KiB、変更先は最大 100 パスです。バイナリ差分とステージ済みの変更があるインデックスは拒否します。`allow_paths` を指定した場合、変更パスはすべていずれかのワークスペース相対 glob に一致する必要があります。受付の承認モードは通常のコミットと同じです。

追加行に個人用パス、メールアドレス、プライベートなホスト名・IP アドレス、認証情報らしい文字列がある場合は、値を表示せず `file:line` を返します。値を確認したうえで取り込みが必要な場合は `override_privacy: true` を指定します。この指定には自動許可モードでも利用者の承認が必要です。承認後は検査済みのパッチを使い、検査後に HEAD またはインデックスが変わっていれば中止します。

作業ツリーで該当パスの内容と実行ビットがコミット前の版と一致する場合だけ、新しい版に揃えます。すでに新しい版と一致していればそのままにし、どちらとも一致しない場合やシンボリックリンク、8 MiB を超えるファイルなどで安全に扱えない場合は、理由とともに `left_untouched` に記録します。`restore_worktree: false` を指定すると復元を省略します。結果には完全なコミット SHA、変更パス、復元の結果が含まれます。

`co_author` には `Name <email>` を指定でき、`Co-Authored-By` トレーラーとして追加します。省略すると、ワークスペース別のサーバー設定 `fuzukue.toml` の `[delegate].git_integrate_co_author` を使います。既定値がなければトレーラーの追加を省略します。

プッシュの既定値は無効です。利用者から依頼があった場合に `push: true` を渡すと、コミットの後に `git_push` と同じ承認経路で現在のブランチを追跡先へプッシュします。承認が得られない場合やプッシュが失敗した場合も、作成済みのローカルコミットの SHA を返します。
