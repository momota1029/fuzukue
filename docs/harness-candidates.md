# ハーネス候補

既存の道具で繰り返し必要な作業を扱えず、スクリプトやパイプラインを組んだときは、MCP の `propose_harness` で候補を登録する。単発の小さな作業は対象外とする。

## 登録

指定する項目は `goal`（目的）、`reason`（既存ツールで足りなかった理由）、`command_or_script`（スクリプトやコマンドの形）、`readonly`（提案する道具が読み取り専用か）と、任意の `suggested_signature`（引数と戻り値の案）。UTF-8 で目的は 512 バイト、コマンドは 8192 バイト、理由とシグネチャはそれぞれ 2048 バイトまで。結果は `id` と `count` を返す。

保存先はワークスペース直下の `harness-candidates/cards/HC-NNN.md`。作業役が別の作業ツリーで動いている場合もワークスペースの候補デッキに記録する。別のワークスペースで使う場合は、ルートに `harness-candidates/deck.toml` と `harness-candidates/cards/` を置く。既定の作業役ツールに含まれ、明示的な許可リストがあるジョブではその設定に従う。

ワークスペース固有のパス、ホスト名、データ、認証情報は、登録前に汎用の引数やプレースホルダーに置き換える。サーバーは全テキスト欄から既知のホームパス、メールアドレス、プライベート IP、tailnet の完全修飾名、既知の認証情報の形式を伏せる。秘密情報らしい断片が残ると保存を拒否する。検出はパターンに基づくため、形式の分からない値や短い内部ホスト名の除去は入力側で行う。保存したスクリプトは説明資料として扱う。

伏せ字処理後の目的とコマンドの形から fingerprint を作る。目的は大文字と小文字をそろえ、コマンドは行ごとに空白をそろえる。同じ fingerprint のカードがあれば `count` と `last_seen` を更新し、備考に出現を追記する。日付は UTC。同じ作業ジョブでの同一候補の再送は一件に数える。その判定に使う `seen_jobs` はサーバーが記録する。書き込みを伴う出現があれば `readonly` は `false` になる。

## 一覧と判断

`list_harness_candidates` は出現回数の降順、同数なら ID 順で一覧を返す。`status` で `candidate`、`accepted`、`rejected`、`merged` のいずれかに絞り込める。`limit` は既定で 20、最大で 50。条件に合う総数は `total`、上限に達して省略した場合は `truncated` で分かる。カードの順序は一覧で決まるため、デッキの `structure.yaml` は省略している。

受付または利用者がカードを読み、採用・見送り・実装済みの判断に応じて frontmatter の `status` を編集する。ロードマップに載せた場合は `promoted_to` に対象の ID（例 `R-01`）を記す。出現回数は判断材料として使い、状態の変更は手動で行う。
