# 選択したスレッドの履歴取得

旧履歴のプロトコル 62 では、サーバーは `resume_from` を省略した接続、値が 0 の接続、ワークスペース切り替えで、アーカイブ済みを含む各スレッドの末尾を先に配信する。Desktop はこれを保持し、スレッドを選び直すと手元の履歴を表示する。Desktop の `thread_history: true` は古いページの取得を有効にする。Android 62 はこのフラグを送らず、受信済みの末尾を表示する。 [従来の初期配信の回帰テスト](../crates/secretaire/src/integration_tests/windowed_history.rs) · [Desktop の選択処理](../crates/fuzukue/src/main.rs#L1329) · [Android の選択処理](../android/app/src/main/java/dev/labgui/remote/RemoteRepository.kt#L233)

## 接続時のメタデータと稼働状態

以下の追加フィールドとイベント名を使う。JSON の型名とフィールド名は既存の規則に従い、スネークケースで送る。

1. クライアントは `Hello` に既存の `protocol`、`workspace`、`resume_from`、`locale`、`platform`、`build_id` を各クライアントの指定に従って載せる。新方式を実装した Desktop と Android は `thread_history: true` と `selection_scoped_transcripts: true` を送る。同じサーバー・ワークスペースの再開には、前回の `ThreadSync.epoch` を `epoch` に、最後に適用したワークスペースの連番を `resume_from` に指定し、有効な取得済み履歴の `cached_sessions`（`session` と `generation` の組）を添える。この一覧が有効なのは `Hello.workspace` の選択に成功した場合に限る。初回取得が未完了のスレッドは一覧に含めない。
2. サーバーは従来どおり `Welcome`、`WorkspaceSelected`、`Workspaces` を返す。新方式を受理した接続の `Welcome` には `selection_scoped_transcripts: true` を付ける。以後のスレッドのデータと履歴応答にはエンベロープの `workspace` を付ける。
3. 選択先の `Threads` は、スレッド ID、タイトル、更新日時、未命名・固定・アーカイブ状態、デッキへの添付・候補、数式マクロ、セッション情報、成果物参照、エージェント設定、GitHub の状態など、既存の `ThreadView` を返す。稼働状態は `ChatActivity` の実行中ターンとスレッド別のワーカー ID、`ChatWaiting` のワークスペースおよび各スレッドの待機理由（利用量による一時停止と再開予定を含む）で知らせる。現在有効な承認と、対応クライアント向けの質問も再提示する。サイドバー・通知・操作可否はこの状態と、ターン・ワーカーの開始と終了、一時停止と再開など対応するライブ更新から求める。本文を開いたことのないスレッドにも表示する。 [メタデータ型](../crates/fuzukue-proto/src/lib.rs#L1228) · [Desktop の状態表示](../crates/fuzukue/src/threads.rs#L484) · [待機状態](../crates/secretaire/src/chat_waiting.rs)
4. 新方式では初回接続とワークスペース切り替えで、選択前の履歴末尾やジャーナルから復元した会話行を配信しない。サーバーはスナップショットの採取とライブ購読の境界を揃え、初期応答の区切りにワークスペース付き `ThreadSync { epoch, through, reset_sessions }`（`seq: 0`）を送る。`epoch` は同じ連番と履歴世代を検証できるワークスペースのストリームを識別し、`through` はこの時点までのワークスペース連番を表す。区切りまでに一覧、現在の稼働状態、再開時に必要な差分を届け、境界より新しいライブ更新は区切りの後に送る。クライアントは適用が完了した時点で連番を確定し、その後に選択中のスレッドの取得を開始できる。

## 初回選択と再表示

- Desktop はメタデータから復元できる選択を優先し、通常の初期選択では最新の非アーカイブスレッドを 1 件開く。開くスレッドがなければ取得しない。Android は新規接続で選択を空にして最初のタップを待つ。通知からの遷移、作成直後の選択、有効な以前の選択の復元も同じ取得経路を通る。 [Desktop の初期選択](../crates/fuzukue/src/main.rs#L1762) · [Android の選択復元](../android/app/src/main/java/dev/labgui/remote/RemoteRepository.kt#L523)
- 選択したスレッドの有効な履歴が手元にないときは、`InWorkspace { id, request: GetThreadTail { session, request } }` を 1 回送る。サーバーは要求を処理する時点のスレッドの状態を採取し、要求元だけに `ThreadTail { session, request, generation, through, events, workers, next_before }` を返す。空のスレッドも成功応答を返す。`generation` は末尾への追加では変わらず、復元や項目の並び・識別子の作り直しで変わる。`through` は、この履歴が取り込んだワークスペースのストリーム上の最後の連番で、履歴本体と同じ時点から採る。履歴応答のエンベロープは `seq: 0` とし、ワークスペースの再開カーソルを進めるのはライブストリームと `ThreadSync` とする。
- 末尾は最大 256 個の連続した保存項目を古い順で返す。予算は履歴イベントの JSON を合計 512 KiB とし、最新の 1 項目が超える場合もその項目を分割しない。連続区間より古い実行中ワーカーの行は例外として先頭側に加え、その ID は `workers` に列挙する。イベントの個数とエンベロープ込みの通信量には、この項目数・バイト数とは別の値が出る。ページ境界の `next_before` は連続区間の先頭項目の序数で、区間が履歴の先頭に届けば空になる。 [範囲の抽出](../crates/secretaire/src/threads.rs#L553)
- 古いページは `InWorkspace` 内の `GetThreadHistory { session, request, before }` で要求する。新方式では要求に `generation`、`ThreadHistoryPage` に同じ `generation` と採取時の `through` を追加する。`before` は排他的で、次の境界があるときは値が小さくなる。非表示の項目を飛ばして表示が 0 行になる場合も、返された境界で先へ進む。既存の Desktop の上端からの追加取得と表示位置の維持を使う。Android の追加取得も同じカーソルを使う。Desktop ではアーカイブ済みを明示的に開く場合も末尾を表示できる。古いページは非アーカイブスレッドで取得できる。 [サーバーのページ取得](../crates/secretaire/src/threads.rs#L1264) · [Desktop の追加と位置維持](../crates/fuzukue/src/chat_history.rs#L306)
- クライアントのメモリ上のキャッシュはサーバー、ワークスペース、スレッド、履歴世代に結び付ける。取得済みの末尾・古いページ、次の境界、反映済みライブ更新、表示位置を保持し、同じワークスペース内で開き直した最初の表示に使う。有効な空の末尾も再利用する。再表示を理由に履歴を要求することはない。未取得・取得中・取得済みを区別し、取得中のスレッドを再選択した場合はその要求を待つ。

## ライブ配信と履歴応答

- 選択は履歴取得の起点であり、ワークスペースのライブ購読は切り替えない。稼働・待機状態、承認、質問、通知は対象スレッドの履歴の有無にかかわらず処理する。選択外でも取得済みの履歴には対象スレッドのライブ更新を反映する。未取得のスレッドでは会話行を積み上げず、初回要求を送ってからその応答までの更新を保持する。それ以前の保存済み更新は要求時点の末尾に含まれる。送信済みプロンプトや承認の確認は、表示用の履歴キャッシュを作らずに処理できる。
- 応答は接続とワークスペースの選択の世代、`workspace`、`session`、保留中の `request` で照合する。古いページでは要求時の履歴世代と境界も照合する。A → B → A と切り替えても、A の応答は A のキャッシュに反映し、B の選択・表示位置・処理状態には影響させない。同じスレッドの重複要求は 1 件にまとめる。両履歴要求の失敗には `ThreadHistoryFailed { session, request, reason }` を返し、一致する保留だけを解除する。`unavailable` では取得済みの行と再試行できる境界を保持し、`not_found` や `stale` ではキャッシュを無効化する。
- 初回応答を適用するときは、まず履歴から行を復元し、採取後（`seq > through`）の保存対象のライブ更新を連番順に適用する。採取時点までの更新は末尾に反映済みなので重ねて適用しない。応答より後に届いた更新にも同じ境界を使う。項目 ID（ワーカーでは job ID も使用）で本文・詳細・ツール呼び出しと結果を関連付ける。分割された本文は連番ごとに一度ずつ連結する。取り消された発言は再表示しない。シーケンス外のライブ操作は到着時に一度だけ処理し、履歴応答の再生から通知・承認・ファイルを開く操作を起動しない。
- 古いページは既存の行と同じ ID の行を重ねず、足りない古い行を時系列に挿入する。連続区間と重なった先行ワーカー行を 1 行にまとめ、最新の進捗・結果を保持する。ページ要求中に届いた結果や本文差分が新たに挿入した行を対象とする場合は、そのページの採取後の更新をその行にも適用する。ページの `through` が適用されるのは、そのページが返した項目の内容に限る。過去のターン終了は履歴の区切りにだけ使い、現在の稼働状態はライブの状態から更新する。表示中の先頭可視項目とその項目内の位置を挿入前後で維持する。 [履歴行の組み立て](../crates/fuzukue/src/chat_history.rs#L423)

## 再接続とワークスペース切り替え

- 同じワークスペースの一時切断では、取得済みキャッシュと表示位置を保持し、保留中の履歴要求を取り消す。`Hello.resume_from` が同じ `epoch` に属し、保管されているジャーナルでその直後から再開できる場合、サーバーは `cached_sessions` のうち世代が一致するスレッドにだけ、取りこぼした会話の差分と発言の取り消しを送る。クライアントは差分と初期スナップショットを `ThreadSync` まで保留し、一緒に反映する。すでに各履歴に含まれる連番は重ねて適用せず、現在の稼働状態には初期スナップショットを使う。再開前から未取得だった選択中のスレッドには、新しい要求 ID で末尾を求める。
- ログの欠落、連番の巻き戻り、`epoch` の変更、履歴世代の不一致、削除、削除後の復元がある場合は、影響したキャッシュを `ThreadSync.reset_sessions`（スレッド ID の配列）または `ThreadHistoryInvalidated { session }` のライブイベントで指定する。欠落範囲を確定できなければ申告されたキャッシュをすべて無効化する。対象が一覧に存在し、選択中なら新たな末尾を 1 回取得し、選択外なら次回の選択まで待つ。復元時も新方式には全履歴を埋め込んだ `ThreadRestored` を送らない。古い応答とカーソルは受理しない。 [選択取得の購読と再開ログ](../crates/secretaire/src/hub.rs#L783) · [現行の復元](../crates/secretaire/src/threads.rs#L2030)
- 別ワークスペースの `WorkspaceSelected` が確定したら、旧ワークスペースの本文・保留中の要求・連番を破棄し、選択の世代を進める。サーバーは新しい選択を通知する前に旧ワークスペースの配信を終了する。クライアントは受信時の接続と選択の世代を確認し、旧世代の本文や応答を捨てる。A → B → A でも、最初の A の要求は新しい A へ適用しない。新しいワークスペースでは初期スナップショットを待ち、選択したスレッドの末尾から始める。切り替えに失敗した場合と、同じ ID の `WorkspaceSelected { replay: false }` では、現在のキャッシュを継続して使う。通知のワークスペース横断配信は本文と独立して扱う。 [サーバーのワークスペース照合](../crates/secretaire/src/main.rs#L1544) · [Desktop の切り替え処理](../crates/fuzukue/src/workspaces.rs#L76)

## プロトコル互換性

サーバーは `min(Hello.protocol, サーバーの PROTOCOL_VERSION)` を `Welcome.protocol` に返す。既存のページ取得条件は、合意値が 62 以上で `Hello.thread_history: true` があること。新方式は同じ下限に加え、クライアントの `selection_scoped_transcripts: true` と、対応サーバーからの明示的な同名の応答を要する。フラグの省略と `false` は従来の配信を選ぶ。クライアントは応答を確認してから新形式の要求を送り、サーバーは受理した接続だけに新方式のイベントと追加フィールドを返す。 [既存の合意処理](../crates/secretaire/src/main.rs#L802) · [Desktop の Hello](../crates/fuzukue/src/conn.rs#L780)

| 接続の組み合わせ | 履歴配信 |
| --- | --- |
| 新方式に対応する Desktop / Android と対応サーバー（合意値 62 以上） | 履歴は選択時に要求し、取得済みのキャッシュを再利用する。 |
| 旧版の Desktop（`thread_history: true`、選択時取得には未対応）と対応サーバー（合意値 62 以上） | 従来の全スレッド末尾と `ThreadHistoryStart`、要求時の古いページ。 |
| Android 62 または他の非対応クライアント（合意値 62 以上、`thread_history` なし） | 従来の全スレッド末尾。古いページは送らない。 |
| 合意値 4–61 | 従来の全スレッド末尾。古いページは送らない。4 未満は従来のスレッド一覧導入前の配信に従う。 |
| 対応クライアントと新方式の応答がないサーバー | その組み合わせで従来利用できた初期配信と再開を使う。クライアント側に新方式のキャッシュしかなく、再接続で応答を得られなかった場合は、カーソルなしで再接続して従来の初期配信を受ける。 |

旧履歴の基準版では Rust と Android がともに 62 だった。指摘台帳の導入で双方が 63 になり、`ReviewFindings` は合意値 63 以上の接続に送る。Android 62 との合意値は 62。R-17 の配布プロトコルは 64。有効化は前述の応答で判定する。Android は古いページ取得に対応するまで従来の配信を使う。 [Android のページ取得](../roadmap/cards/R-18.md) · [配布チェッカー](../scripts/check-android-protocol.sh) · [指摘台帳](review-findings.md)

## 送信した発言の表示遅延を測る

サーバーと Desktop の起動時に `FUZUKUE_SEND_LATENCY_MS=25` を指定すると、25 ms 以上かかった発言について計測結果を出力する。値を 0 にすると対象の発言をすべて採取できる。未設定時は計測しない。サーバーの `send_latency` ログは、WebSocket でテキストフレームを受信した時点からの累積時間をマイクロ秒で記録する。`journal_done_us` はジャーナル追記とバックログへの格納の終了、`transcript_done_us` はスレッドへの反映処理の終了、`broadcast_us` は Hub のライブ配信キューに送った時点を表す。`prompt_lock_wait_us` は送信処理を直列化するロックの待ち時間を単独で記録する。

Desktop の標準エラーには、選択中の取得済みスレッドにライブ更新を適用するまでの時間を `receive_to_apply_us` で出力する。画面の描画と WebSocket 転送は別区間として計測する。ログに本文・ファイル名・認証情報は含めない。同一ワークスペース内ではサーバーと Desktop の `seq` で同じ発言を照合できる。 [負荷時の計測](../roadmap/cards/R-71.md)
