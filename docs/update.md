# クライアントの配布と更新

## サーバーに版を登録する

起動中のサーバーと同じユーザー、プロジェクト、`XDG_STATE_HOME` で実行する。登録先は、プロジェクトのサーバー状態ディレクトリにある `builds/<platform>/`。対応する形式は `windows-x86_64`、`linux-x86_64`、`macos-aarch64` の三つ。

```sh
FUZUKUE_CLIENT_BUILD_ID=<ビルド元のコミットの完全なID> \
  ./target/release/secretaire publish-client linux-x86_64 /path/to/fuzukue /path/to/project
```

最後の引数を省くと現在のディレクトリをプロジェクトにする。`FUZUKUE_CLIENT_BUILD_ID` を省く場合はコマンドを実行したソースツリーの Git HEAD を使う。クライアントもビルド時の同じ変数か Git HEAD を版として記録する。ソースを書き換えてもコミット ID が同じなら、クライアントは同じ版と判定する。

Windows x86-64 向けは WSL から次を実行する。Windows 側の Cargo で共有パス上のソースをビルドし、`C:\Users\<user>\fuzukue-target\release\fuzukue.exe` を登録する。既定のサーバー実行ファイルはこのリポジトリの `target/release/secretaire`。`FUZUKUE_SERVER_BINARY` で変更できる。

```sh
scripts/publish-windows.sh /path/to/project
```

サーバーの自己更新で事前ビルドを指定するには、`~/.config/fuzukue/server.toml` の既存の `[self_update]` に次の行を加える。
```toml
prebuild = [["scripts/publish-windows.sh", "build"]]
```
`publish = ["scripts/publish-windows.sh"]` だけでも同じ事前ビルドが有効になる。点検後、Windows のビルドをサーバーのビルド・テスト・撮影と並行して進める。両方が終わったら作業の終了を待ち、サーバーを入れ替えて正常起動を確認する。確認後に新版サーバーが `scripts/publish-windows.sh register` を実行し、マニフェストを更新して接続中の端末に通知する。

入れ替えに失敗して旧版に復帰したときはクライアントの配布を開始しない。登録だけが失敗したときはサーバーの新版を使い続け、配布工程のログにエラーを表示する。同じサーバー版の次回起動時に保存したビルドから登録を再試行する。独自の配布コマンドは、中断後に同じ引数で再実行しても安全なようにする。

Windows クライアントがビルド先の `fuzukue.exe` から起動している場合も、スクリプトはビルド前にそのファイルを `fuzukue.exe.old` に退避する。`.old` が使用中なら一意な接尾辞を付ける。新しい実行ファイルは元のパスに作られ、起動中のクライアントは再起動するまで動き続ける。
自己更新中の `cargo test` が失敗したときは、失敗したテスト名を特定できた場合に限り、そのテストだけを一度ずつ再実行する。

## 自己更新中の方針作業

自己更新を開始すると、方針役の自動委譲と、使用量の回復や作業完了を受けた計画確認を保留する。同じスレッドの計画確認は 1 件にまとめ、更新状態に保留件数を表示する。利用者の依頼と、それに応じた受付からの委譲は入れ替え待機に入るまで通常どおり受け付ける。

保留した作業は、入れ替えまたは旧版への復帰で起動確認が通ってから再開する。更新が失敗または中止された場合は、稼働中の版で保留を解除する。

ワークスペースの `fuzukue.toml` で設定できる。既定は `true`。`false` にすると、更新準備中は従来どおり自動委譲と計画確認を開始できる。入れ替え待機中は通常の開始制限が適用される。`server.toml` の同じ設定でワークスペース共通の既定を変更できる。

```toml
[delegate]
hold_planner_during_update = true
```

## サーバーの入れ替え待ち

サーバーの更新・昇格・ロールバックでは、新しいターンを止め、開始済みの作業の終了を待つ。実行中のターンから出力が届く、待機対象が終了する、保存エラーが解消するなどの進捗が途絶えてから、既定で 300 秒で強制に切り替える。保留入力の追加だけでは時間を延長しない。秒数は `server.toml` の既存の `[self_update]` で設定する。最短は 1 秒。

```toml
[self_update]
wait_stall_seconds = 300
```

強制ではまず既存の中断要求を送る。5 秒経っても応答しない Claude はプロセスを終了し、送信済みの入力を確認待ちとして記録する。未送信の入力と保留作業は残り、起動確認後に再開条件を満たしたものを配送する。自動強制に切り替えてから 15 秒以内に停止と保存を確認できなければ、待機工程を失敗として稼働中の版に戻る。手動の強制が同じ期限に達した場合は通常の待機に戻り、再度の操作を受け付ける。

接続し直せないときは、サーバーホストから直接ループバックの HTTP を使って待機中の更新を操作できる。設定に合わせてアドレスとポートを置き換える。応答の `started_at` が対象の待機 ID で、`accepts_controls` が `true` の間に操作できる。

```sh
url=http://127.0.0.1:7878/self-update/wait
curl --noproxy '*' --fail-with-body "$url"
```

中止する場合は、取得した ID を `123` の代わりに指定する。

```sh
curl --noproxy '*' --fail-with-body --json '{"started_at":123,"action":"cancel"}' "$url"
```

利用者が強制を了承した場合は、同じ ID を添えて `confirm: true` を指定する。

```sh
curl --noproxy '*' --fail-with-body --json '{"started_at":123,"action":"force","confirm":true}' "$url"
```

HTTP 202 は要求の受理を表す。待機が切り替わった場合や操作を締め切った後には HTTP 409 を返す。HTTP の操作対象は開始済みの自己更新に限る。

## 更新後の配布と整理

新版の起動とヘルスチェックが通ると、`server-builds` に現行版とロールバック用の版を残し、古い版、古いテスト実行ファイル、増分ビルドのキャッシュ、1 時間を超えた一時チェックアウトを整理する。
テスト実行ファイルは名前ごとに最新の一つを残す。削除した件数と容量は入れ替え工程のログに記録する。
`server.toml` の `[self_update]` に `prune = false` を指定すると無効になる。既定は `true`。

`manifest.json` には形式、コミット、実行ファイルの更新日時（`built_at`）、SHA-256、バイト数が入る。実行ファイルはハッシュをファイル名にして保存するため、登録が重なっても取得開始時の版を参照できる。ディスクを整理する場合は配布中のハッシュを残し、取得中の端末がない時に古いファイルを片づける。

## 更新候補を試運転する

受付の `self_update` の `status` は、進行中かどうか、現在の工程、待機理由と待機対象、稼働中のビルド ID、更新元のコミット、エラー、工程ごとの状態を返す。`verbose: true` を指定すると、試運転の詳細と、各工程および試運転ログの末尾最大 40 行（2 KiB まで）を取得できる。

受付で `self_update` の `canary`（`confirm: true`）を実行し、`status`（`verbose: true`）の `canary_status.connect_url` に出る URL をクライアントの「接続」→「リモート」に入力する。既定は `ws://127.0.0.1:7879/ws`。
試運転は Linux / WSL2（Landlock ABI 3 以降）で動く。本番側の設定か `promote`（`confirm: true`）で昇格し、`discard` で破棄する。昇格では入れ替え前に Windows クライアントを事前ビルドし、本番での起動確認後に登録する。
`[self_update]` の `canary_minutes` で自動破棄までの分数を変えられる（既定 30 分）。`canary_project` に指定したサンプルプロジェクトはコピーせず読み書きする。省略すると更新候補のコミットの作業コピーを使う。

## クライアントを更新する

情報欄かサーバー設定に「更新があります」が出たら「更新して再起動」を押す。設定の既定は「更新前に確認」。「自動で入れ替える」を選ぶと、版の違いを検出した時点で取得と再起動を始める。クライアント実行ファイルとその親ディレクトリへの書き込み権限が必要になる。

クライアントはサーバーが現在配布するコミットを取得し、実行ファイルのサイズと SHA-256 を検証する。実行ファイルの更新と起動は更新用プロセスが担当する。Windows では実行ファイルを `.old` に改名して入れ替え、macOS/Linux では旧版を残して新しい実行ファイルをアトミックに置く。新版は WebSocket の Welcome を受け取るまで接続を再試行する。起動確認の期限は 100 秒で、サーバーから入れ替えや終了待ちの通知を受け取った場合は 60 秒延長する。Welcome の前に新版のプロセスが終了するか期限を過ぎた場合は旧版を復元して起動する。失敗したコミットは `.rejected` に記録され、同じ版の更新を繰り返さない。原因を解消して同じ版を再試行するときはこのファイルを削除する。

WebSocket での通知に加えて HTTP で定期確認するため、WebSocket 接続がプロトコルの不一致で拒否された場合も更新できる。どちらも [リモート接続と同じ認証](remote.md) を使う。HTTP は Bearer ヘッダーに対応する。署名の配布と検証は今後の課題。

## 旧版から名前が変わる最初の更新

1. 更新するコミットをチェックアウトし、WSL または Linux で `cargo build --offline --release -p secretaire` を実行する。稼働中の旧サーバーとクライアントを停止する。サービスから起動している場合は、実行ファイルを `target/release/secretaire` に切り替えてから起動する。
2. 旧版と同じユーザー・作業ディレクトリ・プロジェクト引数・XDG 設定で `secretaire` を起動する。旧 `${XDG_CONFIG_HOME:-$HOME/.config}/labo-gui` と `${XDG_STATE_HOME:-$HOME/.local/state}/labo-gui` は、各移行先の `fuzukue` が存在しないときに切り替わる。Windows クライアントは `%APPDATA%`、macOS は `~/Library/Application Support` の設定を同じ規則で移す。状態には配布済みの版、接続トークン、会話、`server-builds` が含まれる。ある場合は移行ログと `server-builds/current`・`previous` のリンク先を確認する。
3. `server.toml` の `[self_update]` に独自の `tests`、`shots`、`publish` を指定している場合は、クレート名とスクリプトに渡す実行ファイル名を新しい名前へ変える。WSL の外で実行ファイルを直接指定する設定、サービス、ショートカットも更新する。
4. WSL で `scripts/publish-windows.sh /実際に開いているプロジェクト` を実行する。Windows Cargo は `C:\Users\<user>\fuzukue-target` を新たに使う。以前の `labo-gui-target` からビルドキャッシュを移す必要はない。PowerShell の `setup-windows.ps1` のビルド先は `%LOCALAPPDATA%\fuzukue\target`。
5. Windows で配布対応の旧クライアント（プロトコル 28 以降）を開き、従来どおり「更新して再起動」を選ぶ。`labo-client.exe` はそのパスで更新される。接続の確認後、同じフォルダに `fuzukue.exe` がなければ作る。既存のショートカットは元のファイルを起動できる。以降は `fuzukue.exe` にショートカットを張り替える。隣の `settings.toml` は両方の実行ファイルで使える。旧版の更新直後の起動試行では復旧に備えて旧設定フォルダを使い、次の通常起動で移行する。

既存の `server-builds/current` が旧版を指している場合、初回はビルドした `secretaire` を明示して起動する。旧サーバーのビルド工程は旧クレート名で固定されているため、改名をまたぐ最初のビルドは手元で行う。旧監督の `self-swap` から切り替える場合は、[サーバーの入れ替え](../cards/design/self-update.md#改名前の監督での入れ替え) の手順を使う。

## この PC をサーバーにする

1. 「接続」設定で Windows は WSL、macOS/Linux はローカルを選び、プロジェクトなどの起動設定を入力する。
2. 「この PC をサーバーにする」を有効にして「サーバーを再起動」を押す。サーバーが動く環境で Tailscale が起動している必要がある。WSL の場合は WSL 内の Tailscale IPv4 アドレスを使う。
3. 設定に表示された URL をコピーし、他の端末の接続設定に入力する。Android アプリでも同じ URL を入力できる。
4. 他の端末のユーザーをサーバー側の [許可リスト](remote.md) に追加するか、接続する端末でトークンを設定する。

サーバーは通常のループバックと Tailscale IP で待ち受ける。同じポートに手動起動したサーバーがいる場合、そのプロセスを止めてからクライアントの起動機能を使う。「クライアントを閉じてもサーバーを残す」を選んで再起動すると、次の通常終了時に起動したサーバーを切り離す。切り離したサーバーを停止するときはサーバーが動く環境で対象プロセスを終了する。

## 端末に送る

設定で「端末に送る」を開き、Tailscale の端末を選ぶ。Windows では Windows の Tailscale を使って一覧と送信を扱う。端末がオフラインなら送信待ちに入り、送信元クライアントの動作中にオンラインになった時点で再試行する。キューは設定ファイルの隣に保存され、クライアントを再起動しても残る。

このサーバーに配布対応クライアントで接続したことのある Tailscale IP には更新通知を送る。接続中の端末はその場で通知を受け、切断中なら次回接続時に最新版を確認する。その他の端末には、登録済みの実行ファイルと、接続先を書いた `settings.toml` を Taildrop で送る。送信形式は端末 OS に対応する上記三形式。受信側では二つのファイルを専用の同じフォルダに置く。macOS/Linux では実行権限を付与する（`chmod +x fuzukue`）。設定ファイルには接続トークンを含めないため、許可リストを使うか受信側で入力する。

Linux で Taildrop が権限不足を返したら、管理者が送信元で `sudo tailscale set --operator="$USER"` を実行して送信するユーザーを登録する。権限を直すと待機中の送信が再試行される。
